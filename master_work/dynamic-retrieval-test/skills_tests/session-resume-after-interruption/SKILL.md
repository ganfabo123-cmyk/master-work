# 会话中断后恢复：先重建状态，再继续执行

## 适用场景

- 会话因 API error / context overflow / 网络错误在中途截断后重新继续；
- 用户回到旧会话说"继续刚才的任务"；
- 新会话承接长任务，且不确定最后一步是否完成。

中断点附近的最后一条 assistant 消息**只是声称**，不是事实——中断可能发生在"声称完成"与"实际完成"之间。

## 处理步骤

1. 恢复任务骨架：从会话历史/TODO/计划文档中重读任务目标与步骤清单。
2. 划分状态：已完成（有证据的）、进行中（不确定的）、未开始。
3. 验证断点：对"进行中"的最后一步，用磁盘/环境事实确认——文件是否存在且内容完整、构建产物时间戳、进程是否残留、数据库/缓存状态。
4. 清理半成品：中断常留下半写的文件、未提交的编辑、残留进程（build/mspdbsrv/test runner），先处理再继续。
5. 从确认无误的断点继续，并在继续的第一条消息里向用户简报：已完成什么、接下来做什么。

## 不要做

- 不要把中断前最后一条 assistant 消息的"已完成"当作事实直接跳过；
- 不要重做已确认完成的步骤（避免重复副作用）；
- 不要在状态未重建前就发起新的修改。

## 证据来源

来自真实 session 审计：c84c0ad3（L468）、47d9fc04（L400）、a20a4070（L990）——三个 session 均因 API error 在任务中途截断，恢复后均出现过重复劳动或状态错乱；该案例是"会话恢复注入"触发器的原型。
