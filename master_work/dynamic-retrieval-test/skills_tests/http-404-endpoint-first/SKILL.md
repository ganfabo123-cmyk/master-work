# HTTP 404 持续出现：先怀疑端点本身，再怀疑代码

## 适用场景

- 接口返回 404 / Not Found，修改处理逻辑、参数、依赖后依旧 404；
- 本地能通、部署环境 404（或反之）；
- 不同接口报 404 但共同点是同一 base URL 或同一代理层。

关键判断：**如果连续两次以上"看似合理"的修改后 404 原样不变，说明修的不是出错的那一层。** 404 的语义是"这个地址上没有资源"，优先级最高的怀疑对象是地址本身。

## 处理步骤

1. 打印/核对完整请求 URL：协议、域名、端口、路径前缀、版本段（/v1/ /api/）、结尾斜杠，逐段与文档或可工作的对照请求比较。
2. 用最小请求验证（curl 或 http 工具）直打该 URL，绕过业务代码，确认 404 是否与代码无关地存在。
3. 检查服务端路由注册：路径是否注册、大小写、前缀拼接是否重复或遗漏（如 `/api` + `/api/users`）。
4. 检查中间层：反向代理/网关 rewrite 规则、静态资源目录、SPA history 回退配置。
5. 以上都排除后，才回到业务代码层排查。

## 不要做

- 不要在 404 未消失的情况下连续改业务逻辑超过两次；
- 不要假设"文档里的 URL 是对的"，以一个确实成功过的请求为基准；
- 不要同时改 URL 和逻辑两处——一次只改一个变量，才能定位。

## 证据来源

来自真实 session 审计：c84c0ad3——404 在多轮不相关修复后依旧存在，agent 长时间被引向错误修复方向；该案例是"触发检索纠偏"的典型原型。
