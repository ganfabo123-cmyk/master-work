# 用户重复报告同一问题：上次修复未生效，用运行证据验证

## 适用场景

- 用户在修复"完成"并声称已解决后，再次报告完全相同的现象；
- 用户原话出现"还是不行 / 还是一样 / 没变化 / still broken / same issue"。

这意味着两种可能之一：修复没有进入实际运行的产物（没编译/没部署/改错文件），或修复改的不是真正的成因。无论哪种，**继续在代码层面推理收益极低**，必须转向运行时证据。

## 处理步骤

1. 停止改代码。列出上一轮修改的文件与声称的效果。
2. 验证修改是否真的在运行的产物里：重新构建/刷新了吗？运行的是哪份代码（路径、端口、缓存）？必要时在修改点加一行明显日志或输出来确认执行路径。
3. 采集实际渲染/运行证据：截图、UI view tree/dump、接口返回、日志时间戳，与用户描述的现象对齐。
4. UI"看不见"类问题按清单排查：元素尺寸是否为 0、opacity/visibility/display、z-index 或层级顺序、父容器 overflow 裁剪、条件渲染分支是否走到、颜色与背景同色。
5. 只有拿到运行证据、确认修复真正生效后，才回复用户。

## 不要做

- 不要凭"代码看起来是对的"再次向用户声称已修复；
- 不要在同一层再叠加一次猜测性修改；
- 不要跳过"确认运行的是新代码"这一步。

## 证据来源

来自真实 session 审计：09d9abe9（Pseudo-OS）——用户两次重新报告同一个视觉 bug，agent 均以代码推演回应而未验证实际渲染，导致返工；该案例是"用户重复抱怨"触发器的原型。
