
# 1 课题来源及研究目的和意义

## 1.1 课题的来源

本课题依托以下国家自然科学基金项目开展：

**（1）多模态数据库自治关键技术研究，国家自然科学基金青年项目（编号：62502126）；**

**（2）面向云边端协同的新型数据管理理论与方法研究，国家自然科学基金重点项目（编号：62232005）。**

随着数字经济、云计算、人工智能和数据要素市场的发展，数据库及其关联的数据管理系统逐渐成为各类数字基础设施的核心组成部分。中共中央、国务院印发的《数字中国建设整体布局规划》将数字基础设施和数据资源体系作为数字中国建设的重要基础，并强调提升数字基础设施能力和数据资源管理能力[1]。国家发展改革委、国家数据局、工业和信息化部联合印发的《国家数据基础设施建设指引》进一步提出建设和运营国家数据基础设施，推动数据高效流通利用，并对基础设施的可靠运行、安全保障和持续服务能力提出要求[2]。这表明，面向大规模、持续运行的数据管理基础设施，提高系统自治运维和故障处置能力已经具有较明确的国家需求背景。([政府网址][2])

与此同时，现代数据管理系统正由传统单机数据库逐渐向云数据库、分布式数据库、多模数据库以及云边端协同的数据管理环境演进。系统内部包含查询处理、事务管理、并发控制、缓存、存储、日志、资源调度和参数配置等多个相互关联的功能模块，外部还需要持续面对动态工作负载和复杂运行环境。在此背景下，系统发生性能退化、锁竞争、资源瓶颈、执行计划异常、参数配置不合理以及多个异常相互耦合等问题时，其故障现象和真实根因之间往往存在较长的传播链路，传统依赖数据库管理员经验进行人工排查的方式面临较高的时间和人力成本。

因此，本课题结合上述国家自然科学基金项目在数据库自治和新型数据管理方面的研究需求，拟研究大语言模型驱动的多智能体故障诊断方法，重点探索复杂数据管理系统中候选根因如何形成、诊断实验如何组织、多源运行证据如何驱动诊断状态持续更新，以及历史诊断过程如何经过长期复用逐步形成可迁移的诊断经验，为复杂数据管理系统的自治诊断和智能运维提供方法基础。

## 1.2 课题研究目的和意义

随着数据管理系统承载的数据规模、业务类型和运行环境不断复杂化，系统运维已经从相对明确的单点故障处理逐渐转向跨查询、事务、配置、资源和基础设施等多个层面的综合诊断。数据库发生异常时，外部通常只能首先观察到查询响应时间上升、吞吐下降、CPU 或 I/O 使用率异常、锁等待增加、连接堆积等表面现象，而这些现象本身并不直接等价于故障根因。例如，同样的查询延迟上升既可能由缺失索引或统计信息过期造成，也可能来源于长事务持锁、内存压力、磁盘 I/O 饱和或其他查询引起的资源竞争。不同异常之间还可能发生传播，使根因与最终可见症状进一步分离。

数据库故障诊断因此并不是简单地将监控指标映射到某一个故障标签，而是一个需要不断获取信息、形成判断并验证判断的连续过程。实际数据库管理员通常会首先根据当前异常提出若干可能原因，再通过查看慢查询、分析执行计划、检查系统监控指标、查询锁和事务状态、检查数据库参数、比较历史负载或者执行针对性的诊断操作进一步获取证据，并依据新的观察结果逐渐排除部分方向，最终确定根因并采取相应恢复措施。DBSherlock、iSQUAD、PinSQL、OpDiag 等研究分别从性能指标、慢查询、根因 SQL 和查询算子等角度证明了数据库故障根因定位的研究价值[4,7,11,18]；近年来 D-Bot、Panda 等工作进一步开始利用大语言模型完成数据库诊断和性能排查[13-14]。D-Bot 已经采用树搜索和协作机制开展复杂异常分析，说明大语言模型能够参与数据库根因诊断过程，而不仅仅用于生成 SQL 或回答数据库知识问题。([Researchr][3])

但是，复杂数据管理系统中的诊断仍然存在明显困难。一方面，系统提供的监控指标、日志、执行计划、查询统计、事务状态和配置项数量较多，如果智能体将所有信息和全部历史操作持续累积在单一上下文中，不仅会增加模型处理无关信息的负担，也容易使早期形成但后来已经失效的判断持续影响后续决策。另一方面，真实故障的调查路径通常无法在任务开始时预先确定。某项证据可能直接排除一个原有怀疑，也可能将一个宽泛的“查询执行异常”进一步细化为“统计信息过期导致执行计划选择错误”等更具体的问题。因此，按照数据库管理员、查询专家、资源专家等固定角色长期划分智能体职责，并不能完全反映实际故障诊断过程中问题结构不断变化的特点。

从这一特点出发，本课题拟首先研究**基于假设实验协同的复杂数据管理系统多智能体故障诊断方法**。对于当前异常，系统将结合已有运行状态形成若干候选根因，并进一步将其中尚不能确定的内容转化为可通过实际数据库状态进行验证的局部诊断问题。例如，当系统怀疑查询延迟由锁竞争导致时，真正需要回答的问题可以进一步具体为“当前阻塞链中的根阻塞会话是谁”“该会话是否长期持有目标对象上的锁”“解除该阻塞后相关请求延迟是否恢复”等。不同诊断智能体围绕这些局部问题调用相应工具获取证据，再由主诊断过程依据实验结果支持、排除或细化原有假设，使根因搜索空间随证据不断收敛。

这种方法关注的不是简单增加智能体数量，而是尝试使多智能体协同结构由当前需要验证的诊断问题决定。不同智能体不必同时维护全部数据库状态和完整诊断历史，而可以围绕相对明确的证据需求开展局部实验。这样既有利于实现上下文隔离，也能够使最终诊断结论与具体观察和运行证据之间保持清晰联系，提高故障诊断过程的可解释性和可追溯性。

除单次故障诊断本身之外，长期数据库运维还具有明显的经验积累特点。数据库管理员在长期工作中形成的专业能力并不仅仅来自数据库手册和固定规则，还来自大量历史故障排查经验。例如，在某种工作负载和数据分布条件下，某类执行计划变化意味着什么；面对某种锁等待结构时应优先检查哪些事务；哪些指标虽然表现异常但通常只是其他故障传播产生的结果。这类经验通常具有较强的条件依赖性，如果直接抽象为无条件规则，容易在新的环境中产生错误迁移；但如果每次故障都被作为完全独立的新任务处理，又会造成大量重复探索。

因此，本课题拟进一步研究**面向数据库故障诊断的诊断经验进化机制**。一次完整诊断结束后，将不直接保存全部长程交互轨迹，也不立即将其压缩为高度概括的规则，而是提取具有局部诊断闭环的 Diagnostic Episode，保留当时的问题现象、运行条件、候选假设、诊断操作、关键观察和局部结论。当后续任务出现相似诊断需求时，系统再主动召回相关历史情景，并结合当前数据库类型、版本、工作负载、查询计划、资源状态和已有证据重新判断其适用性。随着同一历史经验在多个新任务中被反复验证，其表示可以根据实际使用反馈由具体 Diagnostic Episode 逐渐形成具有明确适用条件的 Conditional Experience，并对少量跨任务持续稳定的内容进一步形成 General Rule。

本课题的研究意义主要体现在以下几个方面。

第一，有助于进一步研究大语言模型智能体在复杂数据管理系统自治运维中的连续诊断能力。相比直接根据一次性输入生成根因结论，通过显式组织假设、实验、运行证据和诊断状态，可以使智能体更加接近实际数据库故障排查过程。

第二，有助于探索更加适合故障诊断特点的多智能体协作方式。现有多智能体方法通常围绕固定角色、固定流程或者预设功能组织协作，而故障诊断具有较强的不确定性和动态性。围绕当前待验证问题形成临时、局部的诊断任务，有望减少无效协商和重复分析，使不同智能体的职责与当前证据需求直接对应。

第三，有助于提高复杂数据管理系统自动诊断的可解释性和安全性。数据库运维中的操作可能直接改变运行状态，因此不能仅根据模型生成的自然语言结论执行高风险动作。如果根因判断能够回溯到具体指标、查询、执行计划、锁状态和实验结果，就可以在执行恢复操作前建立更加明确的证据基础。

第四，有助于推动数据库智能体从单次任务求解向长期经验积累发展。通过保存具有上下文条件的诊断情景，并根据后续真实使用情况持续修正和巩固经验，可以避免简单 RAG 或固定知识库只能复用静态文档知识的问题，为长期运行的数据库自治智能体提供更加符合实际运维特点的经验组织方式。

第五，从实际应用角度看，现代云数据库和分布式数据管理系统需要持续处理大量在线业务，故障定位速度和恢复过程安全性直接影响系统可用性。最新 DBA-Bench 在 106 个具有持续工作负载的 PostgreSQL 运维场景中发现，当前自动化 Agent 在 Diagnosis、Outcome 和 Safe Pass 等指标上仍与人工 DBA 存在明显差距，说明面向真实数据库环境的自主诊断仍具有较大研究空间[21]。([arXiv][4])

# 2 国内外研究现状及分析

## 2.1 国外研究现状

### 2.1.1 数据管理系统性能诊断与根因分析研究

数据库故障诊断和性能根因分析长期以来都是数据管理与系统研究的重要问题。早期相关研究主要依赖监控指标、统计模型以及数据库领域知识，从大量系统观测中识别能够解释异常的关键因素。

DIADS 将数据库和存储区域网络的诊断过程进行联合建模，通过机器学习与领域知识结合，从数据库和存储系统产生的大量监控事件中识别潜在根因，并特别关注多个问题并发以及噪声数据条件下的诊断问题[3]。这一工作表明，在复杂数据系统中，仅关注某一个组件容易产生局部判断，而跨层运行信息对于根因定位具有重要作用。([USENIX][5])

DBSherlock 面向事务数据库性能诊断，通过分析正常和异常时间段中的系统指标变化，建立性能异常与系统行为之间的关联，并允许 DBA 反馈进一步改进诊断结果[4]。这一类方法逐渐将数据库诊断由人工逐项检查指标转变为基于监控数据自动发现重要异常因素。随后，相关研究开始进一步关注慢查询、间歇性性能退化以及故障传播关系，使根因定位由“哪个系统指标异常”逐渐下沉到更加具体的数据库对象和执行行为。([Researchr][3])

随着云数据库规模增加，性能故障往往同时受到查询行为和底层资源状态影响。Vista 面向 Amazon RDS 的大规模生产环境建立性能排障框架，通过异常检测筛选异常工作负载，再从大量 SQL 中筛选主要影响查询，并利用因果分析定位造成性能问题的查询及相关统计特征。该系统已用于大规模 RDS 环境，体现了数据库性能诊断在真实云服务中的直接应用价值[15]。([Amazon Science][6])

总体而言，传统数据库故障诊断已经形成从系统级异常检测、指标相关分析，到查询级、执行行为级和跨组件根因定位的发展路线。这些工作建立了较成熟的监控数据、故障注入和根因评价方法，为进一步研究智能体主动参与故障诊断提供了基础。

### 2.1.2 数据库自治管理与智能运维研究

除故障诊断外，数据库领域长期以来也在研究如何减少人工 DBA 对系统调优和运维的参与。OtterTune 利用历史调优数据和机器学习方法自动选择数据库配置参数，证明数据库系统可以根据工作负载和历史经验实现一定程度的自动配置优化[5]。QTune 则进一步将查询特征和数据库状态引入深度强化学习过程，实现面向查询、工作负载和集群等不同粒度的数据库参数调优[6]。这些研究使数据库自治能力逐渐从监控和诊断扩展到优化和行动。([CMU Database][7])

随着大语言模型的发展，研究者开始尝试直接利用模型理解数据库文档、系统状态和运维需求。GPTuner 将 LLM 用于读取数据库手册和异构领域知识，并结合贝叶斯优化完成数据库参数调优，使原本依赖 DBA 手工阅读和积累的知识能够更直接地参与自动调优过程[16]。该研究说明，大语言模型可以在数据库自治系统中承担知识理解和高层决策辅助作用，而不只是完成自然语言到 SQL 等传统任务。([GitHub][8])

Panda 进一步直接面向数据库性能 Debugging 使用 LLM Agent。该方法关注预训练模型容易产生“技术上正确但缺少上下文、难以执行”的泛化建议问题，通过 Grounding、Verification、Affordance 和 Feedback 等机制补充真实数据库环境信息，并提高诊断建议的可执行性[14]。这一研究表明，数据库性能诊断正在由静态模型预测逐渐转向能够结合环境状态和工具反馈进行推理的智能体方法。([VLDB][9])

### 2.1.3 大语言模型智能体与交互式故障诊断研究

数据库之外，云计算和复杂软件系统中的 Root Cause Analysis 近年来也开始快速引入大语言模型智能体。这类研究与数据库故障诊断具有较强共性：系统首先观察日志、指标、Trace 或告警信息，再通过调用外部工具主动获得更多运行证据，最终形成根因判断。

Microsoft 等机构提出的 Automatic Root Cause Analysis via Large Language Models for Cloud Incidents 将大语言模型用于真实云服务事故根因分析，并在生产事故数据上研究 LLM 对历史故障知识的利用能力[23]。随后，Roy 等人在 FSE 2024 中进一步研究基于 ReAct 的 RCA Agent，使智能体不仅根据已有事故描述推理，还能够主动调用检索和外部诊断工具获取日志、指标和数据库等新增信息[24]。这一变化使故障诊断从“对已有观测做推断”逐渐走向“根据当前信息缺口主动获取新的诊断证据”。([EuroSys 2024][10])

AIOpsLab 则从评测基础设施角度研究自主运维 Agent。该框架能够部署服务、注入故障、产生工作负载、导出遥测数据，并提供统一的 Agent-Cloud Interface，使智能体可以在动态运行环境中完成故障检测、定位、根因分析和恢复等任务[27]。与传统静态数据集相比，这类交互式评测环境更适合评价 Agent 是否真正能够通过连续工具调用改变其诊断过程。([MLSys 会议录][11])

此外，Xpert 研究大语言模型如何帮助运维人员生成用于获取遥测信息的诊断查询[26]，MonitorAssistant 则将大语言模型用于大规模云服务监控和异常报告生成[25]。这些工作共同说明，复杂系统运维正在逐步形成“模型理解—工具调用—运行观察—后续决策”的 Agentic Operations 研究范式。([DBLP][12])

### 2.1.4 智能体记忆与经验利用研究

长期记忆是大语言模型智能体研究的重要组成部分。Generative Agents 将历史观察保存为记忆，并通过检索和反思形成能够影响后续行为的高层信息[31]。Reflexion 则利用语言形式的反馈和 episodic memory 保存过去尝试的结果，使智能体能够在后续任务或后续轮次中根据历史失败和成功经验调整策略[30]。

与此同时，ReAct 将推理与外部行动进行交替组织，使模型能够依据工具返回的新观察不断调整后续行为[28]；Tree of Thoughts 则通过显式维护多个候选推理分支，使模型能够在多个可能方向之间进行搜索、评价和回溯[29]。这些研究为“候选假设—外部行动—观察反馈—判断更新”的智能体运行过程提供了重要方法基础。

然而，通用 Agent Memory 通常侧重“过去信息如何存储和检索”，而数据库诊断中的经验具有明显的运行条件依赖。某一诊断结论是否适用往往同时受数据库版本、执行计划、数据分布、参数配置、业务负载和资源状态影响。因此，如何在保留这些条件的同时形成适合跨任务利用的诊断经验，以及历史经验的抽象程度能否随着多次实际复用逐渐变化，仍需要结合数据库故障诊断场景进一步研究。

## 2.2 国内研究现状

### 2.2.1 数据库性能异常与细粒度根因诊断研究

国内高校和企业近年来在数据库性能诊断和根因定位方面开展了较系统的研究，并逐渐形成从指标异常分析到 SQL、执行计划和查询算子级诊断的发展路线。

针对云数据库中的间歇性慢查询问题，Ma 等提出针对 Intermittent Slow Query 的根因诊断方法，将查询性能异常与数据库及主机层面的运行状态联系起来，从而识别导致查询偶发变慢的外部根因[7]。FluxInfer 则针对在线数据库性能异常，通过运行指标之间的关系定位与根因相关的关键 KPI，提高数据库异常排查效率[8]。进一步地，CauseRank 利用因果推断研究 OLTP 数据库性能异常，通过无监督方式识别可能产生故障传播的关键指标[10]。这些研究说明，数据库根因分析已经从单纯异常检测逐渐转向对故障因果关系和传播路径的分析。([VLDB][13])

PinSQL 将诊断粒度进一步下沉至 SQL 层面。该系统将与异常相关的 High-impact SQL 和真正导致性能问题的 Root Cause SQL 加以区分，通过追踪 SQL 之间的影响传播链定位根因 SQL，并进一步执行相应恢复操作。在阿里云生产系统上的实验表明，仅找到“与异常同时发生的 SQL”并不足够，区分相关性和真实根因对于数据库自动诊断具有重要意义[11]。([IEEE Xplore][14])

DBPA 从评测角度构建了事务数据库性能异常 Benchmark，提供多种数据库异常及其复现过程，为数据库性能异常检测和根因诊断提供了统一实验基础[12]。OpDiag 则进一步将故障归因粒度从系统指标和查询下沉到 Query Operator，通过执行计划和运行信息定位具体异常算子[18]。RCRank 综合查询文本、执行计划、执行日志和 KPI 等多模态信息，不仅识别慢查询的可能根因，还进一步按照处理不同根因可能带来的性能收益进行排序[17]。这些工作表明，数据库诊断正在向更细粒度、更丰富观测信息和更直接的根因解释发展。([DBLP][15])

对于分布式数据库中的复杂故障，DBPecker 进一步考虑多个节点和多个基础异常同时存在的 Compound Anomaly，通过图模型描述节点间依赖，并利用考虑因果关系的指标排序定位关键异常[19]。这说明当数据管理系统由单节点向分布式环境扩展后，故障诊断对象也由单一异常逐渐扩展到多个症状之间的传播和耦合关系。需要说明的是，DBPecker 以 PVLDB demonstration paper 形式发表，其主要价值在于展示面向分布式关系数据库复合故障的一体化诊断系统。([VLDB][16])

### 2.2.2 大语言模型驱动的数据库自治诊断研究

国内数据库领域近年来已经开始直接研究大语言模型在数据库自治管理和故障诊断中的作用。

DBMind 在 openGauss 中集成 self-monitoring、self-diagnosis 和 self-optimization 等能力，使数据库能够对慢查询、I/O 竞争等异常进行监控和诊断，并结合学习方法完成参数、索引等自动优化[9]。该工作虽然早于当前大模型 Agent 快速发展的阶段，但已经体现出将数据库监控、诊断与优化组织为自治闭环的研究思想。([VLDB][17])

D-Bot 是近年来较有代表性的 LLM 数据库诊断系统。该系统首先从数据库诊断文档中自动抽取知识，再根据当前任务进行知识匹配和工具选择，并通过 Tree Search 进行 Root Cause Analysis。对于具有多个根因的复杂异常，D-Bot 进一步采用 Collaborative Mechanism 组织多个 LLM 共同诊断。其在包含 539 个异常、覆盖六类典型应用的实验中验证了 LLM 参与复杂数据库诊断的可行性[13]。([VLDB][1])

这一研究表明，多智能体和多步搜索已经能够直接应用于数据库故障诊断，但当前协作过程更多围绕诊断专家和搜索分支展开。本课题拟进一步关注一个更加细粒度的问题：当当前证据不足以判断某个候选根因时，是否可以将“需要回答的诊断问题”本身作为多智能体分解的基本单位，使每个局部 Agent 围绕一个可验证假设主动获取证据，并将其结果用于显式更新整体诊断状态。

2026 年 SIGMOD Industry Track 进一步出现 Learned Root-Cause SQL Prioritization and Diagnosis for Complex Database Performance Issues，继续研究复杂数据库性能问题中的根因 SQL 排序和诊断[20]。这说明工业界和数据库社区仍持续关注复杂数据库性能问题中的根因识别与优先级判断。([2026 SIGMOD/PODS Conference][18])

### 2.2.3 面向复杂系统运维的智能体诊断研究

国内高校与国际工业研究机构合作，也在云服务事故分析和智能运维方向进行了大量探索。Automatic Root Cause Analysis via Large Language Models for Cloud Incidents、MonitorAssistant、Xpert 等研究分别从事故根因生成、异常监控解释和诊断查询推荐等方面说明 LLM 能够参与真实生产系统运维[23,25-26]。

这些研究与数据库诊断虽然面向的具体对象不同，但共享一个重要特点：最终根因通常不能从单一观测直接确定，需要结合日志、指标、查询和其他运行证据进行多轮分析。因此，云服务 AIOps 中逐渐形成的 Tool-Augmented Agent、交互式故障环境和多源观测处理方法，也为复杂数据管理系统自主诊断提供了可以借鉴的技术基础。

## 2.3 国内外文献综述的简析

综合国内外相关研究可以看出，复杂数据管理系统故障诊断已经经历了从人工经验驱动、统计与机器学习分析，到细粒度根因定位以及大语言模型智能体自主诊断的发展过程。

首先，传统数据库性能诊断已经建立了较成熟的问题基础。DIADS、DBSherlock、iSQUAD、FluxInfer 和 CauseRank 等研究证明，数据库性能异常不能仅依赖单个指标进行判断，而需要综合数据库内部状态、系统资源以及不同观测之间的关联和因果关系[3-4,7-8,10]。随着诊断粒度不断细化，PinSQL 将根因分析进一步定位到真正导致性能问题的 SQL，OpDiag 将归因继续下沉到 Query Operator，RCRank 则开始综合 Query、Execution Plan、Execution Log 和 KPI 等多模态信息进行根因识别和影响排序[11,17-18]。这说明“如何从大量异常现象中逐步逼近真正根因”本身已经是数据库领域持续研究的重要问题。

其次，数据库自治研究已经使系统逐渐具备从感知到行动的闭环能力。OtterTune、QTune、DBMind 和 GPTuner 等工作分别从参数调优、查询感知优化、自监控与自诊断以及 LLM 知识利用等角度降低人工 DBA 的参与程度[5-6,9,16]。这些研究为进一步构建能够主动操作真实数据库环境的故障诊断智能体提供了工具和系统基础。

再次，大语言模型的出现正在改变数据库故障诊断的组织方式。Panda 已经直接研究 LLM Agent 如何结合真实上下文完成数据库性能 Debugging；D-Bot 进一步通过工具检索、树搜索和多智能体协作开展根因诊断[13-14]。与此同时，云运维领域的研究也已经表明，Agent 可以根据当前信息主动调用外部诊断工具获得新的日志、指标和系统状态，而不是只对静态输入进行一次性预测[23-27]。因此，数据库自动诊断正在由“根据已有观测预测根因”逐步进入“与运行环境持续交互并主动获取证据”的阶段。

但是，从现有工作来看，仍存在三个值得进一步研究的问题。

其一，**当前数据库诊断 Agent 的多步探索过程虽然已经能够使用工具和搜索策略，但候选根因、待验证问题、实验与证据之间的关系仍缺少更加显式的过程组织。** 当多个根因同时具有可能性时，如果全部信息持续累积在单一 Agent 轨迹中，容易形成较长上下文；而简单按照数据库专家角色或固定步骤拆分多个 Agent，又难以适应诊断过程中问题结构随新证据不断变化的特点。因此，能否将当前的可验证诊断问题作为多智能体动态分解单位，并使 Agent 协作直接服务于候选根因的支持、排除和细化，仍具有进一步研究空间。

其二，**复杂数据库故障诊断不仅需要推理，还需要主动选择具有区分能力的实验。** 对于“缺索引”“统计信息过期”“锁等待”“资源竞争”等不同候选原因，仅继续分析已有文本并不能总是形成可靠结论。智能体需要决定下一步查看哪个执行计划、查询哪组事务状态、比较哪些监控指标以及执行何种低风险验证操作。不同实验能够带来的信息量和成本不同，因此如何围绕当前诊断状态选择有效实验，并利用真实运行证据推动搜索空间收敛，是本课题拟重点解决的问题。

其三，**历史数据库诊断经验如何跨任务持续利用仍缺少与诊断过程本身相匹配的经验组织方式。** 当前 LLM 数据库系统通常主要使用数据库文档、规则或知识库为模型提供背景知识，而历史故障过程中的“当时为什么怀疑某个原因、怎样验证、哪些证据排除了错误方向”包含大量难以从最终故障报告中恢复的信息。直接保存完整轨迹会产生大量冗余，而一次性将其抽象为通用规则又可能忽略经验成立的具体条件。因此，如何以局部诊断情景保存历史过程，在新故障中根据当前上下文重新解释，并依据多次跨任务使用反馈逐步调整经验的抽象程度，是另一个值得进一步研究的问题。

最新 DBA-Bench 的出现进一步说明了上述问题的现实性。该 Benchmark 提供带持续工作负载和多源观测的 PostgreSQL 交互环境，包含 106 个场景和七类运维任务，同时采用 Diagnosis Pass、Outcome Pass 和 Safe Pass 区分“判断正确”“真正解决问题”和“安全地解决问题”。现有自动化系统在安全完成端到端故障处置方面仍明显低于人工 DBA，说明当前数据库 Agent 距离稳定的自治故障诊断仍存在较大差距[21]。([arXiv][4])

综上，现有研究已经为数据库性能诊断、多源运行证据分析、大语言模型工具调用以及智能体记忆提供了良好基础。本课题并不将“是否能够使用 LLM 诊断数据库故障”作为研究问题，而拟进一步关注复杂数据管理系统中**诊断过程如何被组织**：一方面研究如何围绕候选根因构造具有明确证据目标的诊断实验，并通过多智能体协同持续更新诊断状态；另一方面研究历史诊断过程如何形成能够保留适用条件的诊断经验，并通过跨任务实际使用实现动态演化。

# 3 主要内容及方案

## 3.1 总体研究思路

本课题面向复杂数据管理系统运行过程中出现的性能异常和运维故障，重点研究查询执行、事务与锁、数据库配置、系统资源、存储以及多种异常耦合等场景下的自动根因诊断问题。

需要说明的是，本课题所研究的“故障诊断”主要指**数据管理系统在持续运行和业务负载条件下出现的性能退化、配置异常、资源竞争和运行状态异常等 Operational/Performance Faults**，而不以 DBMS 内核源代码缺陷修复或 SQL 语法纠错作为主要研究对象。通过这一范围限定，可以使研究对象与数据库自治运维和 DBA 故障排查场景保持一致。

对于一个待诊断任务，可将基本输入抽象为：

$$
\mathcal{X}=(D,W,O_0,\mathcal{T})
$$

其中，\(D\) 表示当前数据管理系统及其数据库状态，\(W\) 表示正在运行的业务工作负载，\(O_0\) 表示任务开始时已经获得的初始异常现象和观测信息，\(\mathcal{T}\) 表示智能体可调用的诊断工具集合。工具集合可以包括系统指标查询、数据库日志检查、SQL 执行、执行计划分析、慢查询分析、锁和事务状态检查、系统目录查询、参数配置检查以及必要的低风险恢复工具。

本课题预期输出不仅包括最终根因 \(C\)，还包括支持该根因的证据链 \(E\)、采取的恢复操作 \(A\) 以及恢复验证结果 \(V\)，即：

$$
\mathcal{Y}=(C,E,A,V)
$$

在此基础上，本课题拟从两个相互联系但研究对象不同的方向展开。

第一，研究**基于假设实验协同的复杂数据管理系统多智能体故障诊断方法**。该工作关注一次故障任务内部，研究如何从当前观测形成候选根因，将其中存在不确定性的内容转化为可验证诊断问题，再由局部诊断智能体调用真实数据库工具获取新证据，根据实验结果持续更新当前诊断状态并逐步收缩根因搜索空间。

第二，研究**基于诊断情景记忆与跨任务反馈的诊断经验进化方法**。该工作关注多个故障任务之间的长期运行过程，研究如何将前述诊断产生的较长轨迹整理为 Diagnostic Episode，在新任务中按需召回并结合当前上下文重新判断其适用性，再根据多次真实使用反馈逐步形成具有不同抽象程度的诊断经验。

两个研究方向分别对应复杂数据管理系统故障诊断的两个时间尺度。工作一解决“**当前这个故障应该怎样继续查**”，工作二解决“**过去查过的故障怎样帮助以后查得更好**”。工作一产生的结构化假设、实验、证据和局部结论为工作二提供较高质量的经验材料；工作二形成的历史诊断经验又可以进一步参与后续任务的候选假设生成和实验选择，但不会直接替代当前任务中的证据验证。

本课题拟形成如下总体技术路线。

## 3.2 基于假设实验协同的复杂数据管理系统多智能体故障诊断方法

### 3.2.1 多源运行状态与候选根因组织

复杂数据管理系统发生故障时，任务开始阶段通常只能获得部分异常现象。例如用户可能只报告“订单查询突然变慢”，监控系统可能只产生 CPU、I/O 或连接数告警，或者数据库内部出现大量锁等待。上述现象能够说明系统存在异常，但通常无法直接确定根因。

因此，本课题拟首先对当前诊断状态进行显式组织。对于第 \(t\) 轮诊断，将系统状态表示为：

$$
S_t=(F_t,H_t,Q_t,E_t,R_t)
$$

其中，\(F_t\) 表示当前已经确认的事实和有效运行证据；\(H_t\) 表示仍然成立的候选根因集合；\(Q_t\) 表示当前尚待回答的局部诊断问题集合；\(E_t\) 表示此前已经完成的诊断实验及其结果；\(R_t\) 表示当前操作预算和安全约束。

候选根因集合可以表示为：

$$
H_t=\{h_1,h_2,\ldots,h_n\}
$$

候选根因不要求在产生时已经具有较高置信度，其作用主要是将开放式故障空间转化为若干能够继续调查的方向。例如，对于查询延迟异常，可以形成“缺失索引”“统计信息过期”“锁竞争”“资源竞争”“执行计划异常”等候选方向。

但是，宽泛候选原因本身仍不能直接指导 Agent 执行操作。因此，本课题拟进一步将候选根因转换为具有明确观察目标的局部诊断问题。

例如：

```text
候选假设：
H1：查询变慢是由于锁竞争。

↓ 进一步转化

诊断问题：
Q1：当前慢查询是否处于 lock wait？
Q2：如果存在阻塞链，根阻塞事务是哪一个？
Q3：根阻塞事务是否持续占有目标对象上的冲突锁？
```

再例如：

```text
候选假设：
H2：查询变慢是由于统计信息过期导致执行计划退化。

↓ 进一步转化

诊断问题：
Q1：当前执行计划与历史正常计划是否发生关键变化？
Q2：优化器估计基数与实际基数是否存在明显偏差？
Q3：更新统计信息后计划和执行性能是否恢复？
```

通过这种方式，本课题拟将“继续分析数据库问题”转化为“当前最需要通过实际证据回答哪个问题”，使后续多智能体协作能够围绕真实信息缺口开展。

### 3.2.2 面向局部诊断问题的实验式多智能体协同

在形成局部诊断问题后，本课题拟采用多智能体方式组织验证过程。

其中，主诊断智能体主要维护当前整体诊断状态，负责判断“**现在还不确定什么，以及下一步最值得验证什么**”。当某一候选原因需要进一步验证时，主诊断智能体将根据当前证据形成局部诊断任务，并交由相应 Detector Agent 完成。

Detector Agent 不重新承担整个故障的全局根因搜索，而主要围绕当前局部问题进行工具选择、证据采集和实验判断。根据问题类型，Detector Agent 可以调用不同类型工具，包括：

* 查询系统指标和时间序列；
* 检索数据库和系统日志；
* 获取慢查询及执行统计；
* 执行 `EXPLAIN` 或在安全条件下执行受控的 `EXPLAIN ANALYZE`；
* 查询系统目录和索引状态；
* 查询 session、transaction 和 lock 状态；
* 检查数据库参数和资源配置；
* 比较异常时段与正常时段运行状态；
* 在隔离环境中执行必要的验证性操作。

为了控制主动诊断的风险，本课题拟将工具操作按照影响范围划分为不同等级。只读查询、监控读取和执行计划检查可作为低风险诊断操作优先使用；可能增加系统负载但不修改持久状态的实验需要考虑资源预算；涉及终止会话、修改参数、创建索引或其他持久状态变化的操作则主要放置在根因已经获得较充分证据支持后的恢复验证阶段执行。

一次局部诊断实验拟表示为：

$$
e_i=\langle q_i,a_i,o_i,v_i,c_i\rangle
$$

其中，\(q_i\) 表示待验证的局部诊断问题，\(a_i\) 表示 Agent 为回答该问题选择的工具或实验操作，\(o_i\) 表示实际获得的观察结果，\(v_i\) 表示能够验证该观察的原始运行证据，\(c_i\) 表示实验对当前候选假设形成的局部结论。

局部结论主要包括：

$$
c_i \in
\{\text{Support},\text{Reject},\text{Refine},\text{Uncertain}\}
$$

即当前实验可以支持原有假设、排除原有假设、要求进一步细化假设，或者由于证据不足暂时无法判断。

### 图 3-2 基于假设实验协同的多智能体在线诊断流程

```text
                当前数据库异常状态 S_t
                         ↓
                生成候选根因集合 H_t
                         ↓
              构造待验证问题集合 Q_t
                         ↓
             评估证据需求 / 风险 / 成本
                         ↓
                  选择诊断问题 q_t
                         ↓
                  调度 Detector Agent
                         ↓
             ┌───────────┼───────────┐
             ↓           ↓           ↓
         SQL/Plan      Lock/Txn    Metric/Log
          Agent         Agent        Agent
             ↓           ↓           ↓
          执行局部、可验证、受控诊断实验
                         ↓
            Observation + Raw Evidence
                         ↓
          Support / Reject / Refine / Uncertain
                         ↓
                  更新诊断状态 S_t+1
                         ↓
              ┌──────────┴─────────┐
              │                    │

              │                    │

```

通过该机制，主诊断智能体和 Detector Agent 之间主要通过结构化的局部问题与证据结果进行通信，而不是进行无边界的自然语言讨论。研究中将进一步比较这种动态问题驱动协同方式与单 Agent、固定角色多 Agent 以及直接工具调用方法之间的差异。

### 3.2.3 基于多源运行证据的诊断状态更新

复杂数据管理系统诊断能否有效推进，关键并不在于一次产生多少候选根因，而在于新获得的运行证据能否真正改变当前判断。

因此，当 Detector Agent 完成一次实验 \(e_i\) 后，本课题拟通过状态更新函数：

$$
S_{t+1}=\mathcal{U}(S_t,e_i)
$$

重新调整当前候选根因、有效事实、待验证问题以及后续实验优先级。

对于获得明显反证的候选方向，应降低其优先级或者从主要搜索空间中移除；对于获得部分支持但仍不足以确定根因的候选，应进一步细化为更具体的假设；如果实验过程中出现此前未考虑到的新异常，则允许重新产生新的候选根因。

需要指出的是，本课题所强调的“搜索空间收缩”并不意味着候选数量必须在每一轮严格单调减少。真实数据库故障中，一个实验可能排除一个宽泛假设，但同时暴露多个更具体的异常。因此，本课题关注的是随着有效运行证据不断积累，系统对于最终根因的**总体不确定性逐渐降低**。

对于不同 Agent 返回的证据，还需要考虑证据冲突和可信度问题。例如，一个指标异常可能支持资源竞争假设，但执行计划分析又显示当前 SQL 本身存在明显退化。本课题拟保留每项局部结论与其原始证据之间的关联，在关键结论出现冲突时触发补充实验或交叉验证，而不是直接依赖单次自然语言判断更新全局状态。

通过显式维护诊断状态，可以使当前 Agent 主要关注仍然有效的事实和候选方向。已经被明确反证的假设、无关工具输出和长期不再影响当前判断的历史信息不需要持续占据主要上下文，仅保留在完整诊断日志中供追溯和后续经验构建使用。

### 3.2.4 根因收敛与安全恢复验证

随着多轮局部实验和状态更新持续进行，当某个候选根因获得较充分的直接或间接证据支持，同时其他主要候选方向已经被排除或者显著弱化时，本课题拟进入根因确认阶段。

根因确认不以模型单次生成的“高置信度判断”为主要依据，而要求能够形成从原始异常到最终根因的可追溯证据链。例如：

```text
业务查询延迟明显上升
        ↓
发现大量 lock wait
        ↓
定位根阻塞 Session A
        ↓
发现 Session A 长期执行 SQL X
        ↓
SQL X 因缺失索引发生大范围扫描
        ↓
事务持续时间显著增加并长期持锁
        ↓
其他事务形成阻塞链
        ↓
根因：
SQL X 缺失关键索引导致长事务，
进一步产生锁竞争并引发整体查询延迟
```

这种证据链能够区分“观察到的直接症状”和“真正导致故障发生的根本原因”。

根因确认后，系统可以根据故障类型生成相应恢复建议或在隔离评测环境中执行恢复操作，例如更新统计信息、创建或调整索引、终止异常会话、修改参数或者恢复资源限制。本课题不将具体数据库优化算法本身作为独立研究重点，而主要将恢复操作视为诊断结论是否正确的外部验证。

恢复后需要重新观察原始异常指标、业务工作负载以及数据库整体状态。如果原始问题得到解决且没有引入新的异常，则认为此次诊断闭环完成；如果故障仍然存在，则将恢复结果作为新的证据重新进入诊断循环。

## 3.3 基于诊断情景记忆与跨任务反馈的诊断经验进化方法

### 3.3.1 长程诊断轨迹的 Diagnostic Episode 构建

一次数据库故障诊断完成后，系统通常会留下较长的执行轨迹，其中不仅包含最终根因和恢复操作，还包含大量候选假设、SQL 查询、执行计划、监控结果、失败实验、被排除方向和中间判断。

如果将整条 Trace 直接作为一条长期记忆，在后续任务中可能面临内容冗余、粒度过大以及有效信息难以定位的问题；如果仅在任务结束时生成一句“此类问题通常由缺失索引导致”的总结，又容易丢失这一经验成立时所依赖的工作负载、执行计划和证据条件。

因此，本课题拟将长程诊断轨迹进一步重构为多个具有局部诊断闭环的 **Diagnostic Episode**。

第 \(i\) 个诊断情景可以表示为：

$$
M_i=
\langle
p_i,c_i,h_i,q_i,a_i,o_i,e_i,r_i
\rangle
$$

其中：

\(p_i\) 表示该情景需要解释的问题或局部症状；

\(c_i\) 表示当时数据库、工作负载和系统环境中的关键上下文条件；

\(h_i\) 表示当时形成的候选假设；

\(q_i\) 表示需要回答的局部诊断问题；

\(a_i\) 表示采取的诊断行动或实验；

\(o_i\) 表示实际观察结果；

\(e_i\) 表示支撑结论的关键证据；

\(r_i\) 表示最终形成的局部诊断结论。

例如，在一次最终根因为缺失索引的故障中，系统可能首先怀疑锁模块异常，但通过阻塞链检查发现锁等待只是某条慢 SQL 导致长事务产生的次生症状，从而完成一个“锁竞争是否为直接根因—检查阻塞链—发现锁等待为传播结果—排除直接锁故障”的局部诊断闭环。即使这一 Episode 并未直接定位最终根因，其中仍然包含有价值的排除性经验，因此可以独立保存。

### 3.3.2 历史诊断情景的主动回忆与上下文反思

历史经验并不需要在每个新任务开始时全部加入上下文。本课题拟采用按需召回方式，在当前诊断出现明确经验需求时检索相关 Diagnostic Episode。

经验需求可能出现在以下情况：当前存在多个相近候选根因难以区分；连续实验没有获得有效信息；当前执行计划或故障症状与历史案例表现高度相似；或者当前需要寻找过去使用过的某类诊断实验。

检索时可以综合当前异常类型、数据库状态、SQL 特征、执行计划、候选根因、已经执行的实验和现有证据进行匹配。具体检索算法不是本课题主要创新目标，可采用关键词检索、向量检索或混合检索等成熟方法。

但检索到历史经验之后，本课题不拟直接按照历史结论采取行动，而将增加 **Contextual Reflection** 过程。

该过程主要回答：

```text
当前任务与历史 Episode 的哪些条件真正相同？
            ↓
数据库版本、数据分布、工作负载和配置是否存在关键差异？
            ↓
历史故障中的因果链是否可能在当前环境重新成立？
            ↓
历史实验方法是否值得复用？
            ↓
历史局部结论能否迁移？
            ↓
采用 / 部分采用 / 不采用
```

例如，历史情景可能表明“Seq Scan + 高 CPU”最终由缺失索引造成，但当前任务虽然具有相似表面现象，却可能由于过滤条件选择性过低而使 Seq Scan 本身成为合理执行计划。因此，历史经验只能作为当前诊断的参考，需要由当前证据重新验证。

### 图 3-3 历史诊断经验的召回与上下文反思流程

```text
                     当前诊断状态 S_t
                            ↓
                      出现经验需求
                            ↓
               检索相关 Diagnostic Episode
                            ↓
                      获得历史情景 M_i
                            ↓
                 ┌──────────────────────┐
                 │ Contextual Reflection │
                 ├──────────────────────┤
                 │ 当前症状是否相似？     │
                 │ 工作负载是否相似？     │
                 │ SQL / Plan 是否相似？ │
                 │ 数据与配置条件是否一致？│
                 │ 历史因果关系是否可迁移？│
                 │ 哪些实验值得复用？     │
                 └──────────┬───────────┘
                            ↓
                  采用 / 部分采用 / 不采用
                            ↓
                   进入当前诊断过程
                            ↓
                   记录实际使用结果
```

### 3.3.3 跨任务经验使用记录与适用性分析

某条经验是否具有稳定迁移价值，仅根据其原始任务中的一次成功诊断难以判断。

因此，本课题拟记录每个 Diagnostic Episode 在后续不同任务中的实际使用情况。对于历史经验 \(M_i\)，其第 \(k\) 次复用记录可以表示为：

$$
u_i^k=
\langle
C_k,\rho_k,\alpha_k,y_k
\rangle
$$

其中，\(C_k\) 表示本次召回时的新任务上下文；\(\rho_k\) 表示 Contextual Reflection 对历史经验适用性的判断；\(\alpha_k\) 表示历史经验是否被采用以及采用了哪些内容；\(y_k\) 表示经验实际使用后的后续结果。

如果某一 Diagnostic Episode 在多个数据库实例和不同故障任务中反复被召回，并且其关键适用条件、有效实验和局部结论具有较高一致性，则可以认为其中存在更加稳定的可迁移诊断知识。

反之，如果某条历史经验经常因为表面症状相似被召回，但在上下文反思阶段反复发现关键条件不同，或者采用后频繁产生错误方向，则说明该经验具有较强上下文依赖，不应进一步泛化。

由此，经验是否可靠不再只由任务结束时模型的一次总结决定，而能够由跨任务真实使用反馈持续修正。

### 3.3.4 基于复用反馈的自适应经验进化

在获得跨任务使用记录后，本课题拟进一步研究历史经验的表示形式是否可以随长期使用逐步变化。

经验初次产生时，优先以 Diagnostic Episode 形式保留较丰富的原始条件、实验和证据。随着后续任务不断召回该经验，可以进一步分析其中哪些诊断判断长期依赖特定上下文，哪些内容已经表现出更加稳定的迁移能力。

当某个 Episode 的部分诊断启发在多个任务中表现稳定，但仍需要满足明确条件时，可以进一步形成 **Conditional Experience**。例如：

> 当某类 OLTP 查询出现持续延迟、执行计划由 Index Scan 转为 Seq Scan，同时基数估计与实际结果存在明显偏差时，应优先验证统计信息是否过期。

这种经验不再保留原始任务的全部细节，但明确保存适用条件。

当某些诊断原则在更加广泛的数据库实例、任务类型和上下文中持续稳定时，可以进一步抽象为 **General Rule**。

因此，本课题拟研究的经验进化关系可概括为：

$$
\text{Diagnostic Episode}
\rightarrow
\text{Conditional Experience}
\rightarrow
\text{General Rule}
$$

但这一过程不是所有经验必须经历的固定链路。高度依赖原始上下文的经验可以长期停留在 Diagnostic Episode；部分稳定的经验可以形成 Conditional Experience；只有跨任务表现长期一致、对具体数据库状态依赖较弱的内容才考虑进一步形成 General Rule。

同时，高层经验仍保留与来源 Diagnostic Episode 和原始证据之间的关联。如果已经抽象的经验在新任务中明显失效，系统可以重新回溯其来源，判断此前是否遗漏了重要适用条件，并根据新的复用结果降低其泛化程度或修改经验内容。

### 图 3-4 基于跨任务反馈的诊断经验进化流程

```text
                Diagnostic Episode M_i
                          ↓
                 在后续任务中被召回
                          ↓
                  Contextual Reflection
                          ↓
                 采用 / 部分采用 / 拒绝
                          ↓
                   记录实际诊断结果
                          ↓
                   跨任务使用记录 U_i
                          ↓
              分析稳定性与上下文依赖程度
                          ↓
        ┌─────────────────┼─────────────────┐
        ↓                 ↓                 ↓
   高上下文依赖       条件较稳定        跨任务高度稳定
        ↓                 ↓                 ↓
Diagnostic Episode   Conditional       General Rule
                     Experience
        └─────────────────┬─────────────────┘
                          ↓
                  后续新任务继续验证
                          ↓
             有效则强化 / 失效则回溯修正
```

这里所研究的“诊断经验进化”主要指**外部非参数记忆中的经验内容、适用条件和表示粒度根据跨任务使用反馈发生变化**，不涉及持续更新基础大语言模型参数。

## 3.4 实验方案与评价方法

本课题拟采用公开 Benchmark 与可控数据库实验环境相结合的方式开展实验。

首先，拟重点采用 **DBA-Bench** 作为端到端 Agent 故障诊断评测环境。DBA-Bench 提供持续运行的 PostgreSQL、真实工作负载、多源观测和可执行运维接口，包含 106 个场景和七类数据库运维任务，并通过 Diagnosis Pass、Outcome Pass 和 Safe Pass 分别评价根因判断、问题是否真正解决以及恢复过程是否安全[21]。这类交互式评测环境与本课题“通过实验主动获取新证据”的研究方式较为匹配。([arXiv][4])

其次，拟采用 **DBPA** 作为可控性能异常诊断实验基础。DBPA 提供数据库性能异常的复现过程和数据，可用于分析不同异常类型下候选假设生成、局部实验以及诊断状态更新机制的表现[12]。

根据实验需要，还拟建立可控 PostgreSQL 故障环境，通过容器快照、固定工作负载和故障注入脚本构造缺失索引、统计信息异常、锁等待、资源瓶颈、配置问题及部分复合故障，用于开展机制级消融实验和跨任务经验复用实验。

对于工作一，拟重点比较：

```text
单智能体直接诊断
        VS
固定流程 / 固定角色多智能体
        VS
假设—实验协同多智能体
```

评价指标除最终故障解决率外，还包括根因定位准确率、Diagnosis Pass、Outcome Pass、Safe Pass、工具调用次数、诊断轮数、总 Token 消耗、峰值单 Agent 上下文长度和诊断时间等。

对于工作二，拟设计跨任务实验，将历史诊断任务与后续评测任务进行划分，并比较：

```text
无历史记忆
      VS
完整 Trace 记忆
      VS
任务级摘要记忆
      VS
Diagnostic Episode
```

重点分析历史经验是否提高后续诊断成功率、减少无效工具调用和重复实验，同时评价历史经验导致错误方向的负迁移情况。

通过上述实验，本课题拟不仅回答“最终是否诊断成功”，还进一步分析成功或失败发生在候选假设、诊断实验、证据解释、状态更新还是经验迁移等哪个环节，使研究结论能够对应到所提出的具体机制。

# 4 预期达到的目标

本课题面向复杂数据管理系统运行故障，拟围绕单次任务中的假设实验协同诊断以及跨任务诊断经验长期利用开展研究，预期达到以下目标。

首先，形成一种面向复杂数据管理系统故障的结构化诊断状态表示方法。能够统一维护当前有效运行事实、候选根因、待验证诊断问题、已完成实验及安全约束，使故障诊断不再主要依赖不断增长的自然语言交互轨迹，而可以依据新的运行证据持续支持、排除和细化候选根因。

其次，设计并实现一种基于假设实验协同的多智能体故障诊断方法。该方法能够根据当前数据库异常和已有证据形成候选根因，将尚不确定的判断转换为局部可验证诊断问题，并调度 Detector Agent 使用指标、日志、SQL、执行计划、锁状态、事务状态和配置等工具开展针对性实验，以新获得的运行证据推动根因搜索空间逐步收敛。

再次，形成一种面向长程数据库诊断轨迹的 Diagnostic Episode 表示方法，使历史诊断过程能够以具有“问题—假设—实验—观察—证据—结论”局部闭环的形式进行组织，降低完整轨迹过长和高度抽象规则丢失上下文之间的矛盾。

在此基础上，研究历史诊断情景的主动召回和 Contextual Reflection 机制，使智能体在新的数据库故障任务中能够结合当前系统状态重新判断历史经验的适用性，而不是直接复制过去的诊断结论或恢复操作。

进一步形成基于跨任务复用反馈的诊断经验进化机制，使历史经验能够根据长期实际使用结果保持为 Diagnostic Episode、逐步形成 Conditional Experience，或者在具有充分跨任务稳定性的情况下进一步形成 General Rule，并支持经验失效后的回溯和修正。

最终，完成相应多智能体数据库故障诊断原型，并在 DBA-Bench、DBPA 以及可控数据库故障环境上开展系统实验，对方法的根因诊断能力、恢复效果、安全性、运行成本和历史经验迁移效果进行分析，明确所提出方法的有效性、适用范围与主要限制，并完成硕士学位论文。

# 7 为完成课题所需的条件

本课题主要需要大语言模型智能体运行环境、可交互数据库实验环境、多源数据库观测工具、容器化故障复现环境以及完整的执行过程记录和分析工具。目前已经具备大语言模型调用、多智能体 Harness 开发和工具执行等基础条件，后续主要需要进一步完善数据库侧实验环境。

首先，需要具备能够支持工具调用和长程任务的大语言模型及多智能体运行框架。基础模型需要具备较好的自然语言推理、数据库知识理解和 Function Calling 能力，系统层面需要支持不同 Agent 的动态创建、上下文隔离、任务调度以及结果返回。模型可以采用可替换接口，以避免研究结论仅依赖单一模型。

其次，需要建立可重复运行的数据库实验环境。后续拟以 PostgreSQL 为主要实验系统，通过 Linux 和 Docker 等工具隔离不同故障场景，并使用容器快照或数据库状态恢复机制保证不同实验之间的可重复性。DBA-Bench 和 DBPA 可以分别作为端到端 Agent 运维和数据库性能异常诊断的主要公开评测基础。

再次，需要提供较完整的数据库诊断工具集合，包括数据库日志、慢查询、执行计划、系统目录、事务与锁状态、数据库参数、操作系统 CPU/内存/I/O 指标以及必要的 workload 执行接口。根据实验需要，还可以使用 PostgreSQL 自身统计视图以及 Prometheus 等监控工具构建多源观测环境。

由于本课题包含主动诊断和恢复验证，还需要通过容器、权限控制和快照恢复等方式隔离高风险操作。在真实或共享数据库上原则上仅执行只读诊断；涉及参数调整、索引修改、会话终止等操作主要在专用实验实例和 Benchmark 环境中进行。

此外，需要建立较完整的诊断过程数据库，统一记录 Agent 输入输出、工具调用、原始证据、候选假设变化、实验结果、诊断状态、恢复操作以及历史经验召回和使用情况，为后续消融实验、失败案例分析和诊断经验进化研究提供数据基础。

总体而言，本课题不涉及大规模基础模型训练，主要计算开销来自 LLM 推理、数据库 workload 执行和多轮故障实验，因此现有服务器、容器环境以及模型调用资源能够基本满足研究需要，具有较好的可实施性。

# 8 研究过程中可能遇到的问题以及解决的措施

考虑到本课题包含交互式数据库故障环境、多智能体诊断和长期经验利用，为避免研究范围过度扩张，研究过程中拟重点关注以下三个可能影响课题实施的问题。

## 8.1 数据库故障环境和复杂诊断任务的稳定复现问题

数据库性能异常通常受到数据规模、并发负载、系统资源和运行时序等因素影响，同一故障在不同实验运行中可能表现出不同强度，复合故障的稳定复现难度更高。如果实验环境本身不稳定，可能使 Agent 方法差异与环境随机波动混合，影响实验结论可靠性。

针对这一问题，后续研究拟优先采用 DBA-Bench、DBPA 等具有明确场景定义或故障复现流程的公开环境，并通过 Docker、固定数据快照、固定 workload 和场景级故障验证条件控制实验状态。对于自行补充的故障场景，仅选择能够通过明确条件重复注入和验证的典型问题，不追求覆盖所有数据库故障类型。重要实验将进行多次重复运行，并分别记录故障是否成功注入、任务初始状态和最终恢复状态。

## 8.2 多源证据存在噪声以及主动诊断操作可能产生错误判断或安全风险

复杂数据库故障中，不同监控指标和运行现象可能同时异常，其中部分只是根因传播产生的次生症状。与此同时，大语言模型可能错误解释执行计划、日志或工具返回结果。如果错误证据直接进入全局诊断状态，还可能使后续搜索持续偏离正确方向。

针对这一问题，本课题拟保存每项诊断结论与原始工具输出之间的证据关联，使重要判断能够回溯到具体 SQL、执行计划、指标、日志或锁状态。对于存在冲突或直接决定最终根因的重要证据，可以通过补充实验、重复检查或不同 Agent 交叉验证提高可靠性。

在主动操作方面，将诊断工具按照风险进行分级，优先采用只读、低影响的证据获取操作。涉及状态修改的高风险操作主要在隔离实验环境中执行，并在执行前要求已有较充分根因证据，同时利用数据库快照和恢复机制控制实验风险。

## 8.3 多智能体运行成本与历史诊断经验负迁移问题

多智能体能够将不同局部诊断问题进行隔离，但同时也可能增加模型调用次数、Token 消耗和工具执行时间。如果局部问题划分过细，还可能出现多个 Agent 重复读取同一状态和执行相似实验的问题。另一方面，随着历史 Diagnostic Episode 数量增加，错误或者仅在特定上下文有效的经验也可能对新的诊断产生负迁移。

因此，在线诊断阶段将结合当前问题的重要程度、已有证据和预估工具成本决定是否需要独立调度 Detector Agent，并通过工具调用次数、Token、诊断时间和每次实验是否实际改变诊断状态等指标分析额外成本是否合理。

历史经验方面则不允许“召回即执行”，而通过 Contextual Reflection 检查数据库环境、工作负载、查询计划、配置和证据条件是否一致。经验进化过程采用相对保守的策略，只有经过多个任务持续验证的内容才进一步抽象；同时保留高层经验和来源 Diagnostic Episode 的关联，当经验在新任务中失效时能够回溯原始条件并进行修正。通过上述方式控制多智能体额外开销以及长期经验带来的负迁移风险。
