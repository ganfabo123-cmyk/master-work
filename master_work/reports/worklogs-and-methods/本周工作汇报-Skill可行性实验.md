# 本周工作汇报：Coding Agent Skill 提取与动态管理可行性实验

## 1. 轨迹数据整理与研究方向

### 1.1 实验素材

本周首先从 Hugging Face 获取 30 个真实 Coding Agent 工作轨迹，作为后续切片、聚类、Skill 提取和检索实验的共同素材。现有材料记录这批轨迹由 28 个 Claude 会话、1 个 Cursor 会话和 1 个 OpenCode 会话组成，内容保留用户输入、模型分析、工具调用、工具结果和后续修正过程。

本周没有把这些轨迹重新加工成少量人工案例，而是尽量保留原始执行顺序。原因是 Skill 不只是一个“解决方案摘要”，还应当包含问题是如何出现的、模型依据什么信号开始处理、采取了什么操作以及最后如何验证。后续所有版本都使用同一批 30 个轨迹，保证不同处理方式之间可以直接比较。

### 1.2 动态切片

在完整轨迹基础上进行了动态切片，把长会话拆成相对完整的局部问题处理过程。经过多种切片方式比较，最终采用置信度优先方法的衍生版本：

`calibrated-confidence-length-banded-v3-slices`

该版本综合考虑语义变化、轨迹长度和局部上下文完整性，输入 30 条轨迹，输出 97 个切片，且每个切片都可以回溯到原始来源。选择它的原因不是切片数量最多，而是它在规模控制和问题因果完整性之间表现最好。

切片过程也修正了一个早期认识：切得越细不一定越适合检索。过细的切片容易把“出现错误、分析原因、修改代码、重新验证”拆开，模型虽然看到更短的文本，却看不见经验为什么成立。因此最终把切片看成一种组织材料的方式，而不是对原始轨迹的替代。

## 2. 聚类与 Skill 提取路线探索

### 2.1 从领域聚类到行为模式聚类

在 97 个切片基础上，先进行领域聚类，最终整理出 8 个较细领域。领域聚类能够把技术主题相近的切片放在一起，方便浏览和分析，本身没有明显问题。随后又增加成功、失败和无法判断三类结果标签，用来观察同一领域内部的结果差异。

在此基础上继续尝试行为模式聚类，使用工具调用顺序、操作类型、文件类型和轨迹规模等信息形成行为原型。结果表明，行为相似不等于经验相同：不同问题可能使用相似工具，同一问题也可能因环境不同采用不同操作。

因此，本周逐步明确了一个重要区别：领域聚类有分析价值，但聚类结果不能直接等价为 Skill。聚类能回答“哪些材料相近”，却不能自动回答“哪一条经验可以在新任务中复用”。这也是后来放弃把复杂聚类作为 Skill 提取核心步骤的原因。

### 2.2 从通用抽象转向可识别的专属 Skill

继续检查轨迹后发现，完全脱离工程环境的通用 Skill 很难同时做到准确和可执行。描述太抽象，模型无法据此行动；描述太具体，又会退化为某个项目的操作记录。

相对容易抽象的是由稳定信号定义的专属类型，例如错误码、异常类型、错误消息模板、测试用例名称、调用栈位置、配置变化、依赖版本和文件类型。这样的信号能够先回答“什么时候可能遇到这个问题”，再由 Skill 说明“遇到后应该怎样排查和修复”。

已有分组的人工检查显示，68 个错误、调用栈、配置和依赖相关分组中，约 24 个具备较完整的可提炼经验，约占 35.3%。这不是最终命中率，而是说明 Skill 提取需要先找到稳定的问题边界，不能把所有成功轨迹都强行转化为通用 Skill。

### 2.3 A/B/C Skill 提取对比

为了比较上下文组织方式，使用同一批任务分组进行了三种 Skill 提取实验：

- **A：原始轨迹**。直接阅读完整任务轨迹，14 次全部完成，得到 24 个 Skill，总 token 约 2849.9 万。
- **B：切片轨迹加折叠后的原始上下文**。用切片组织重点，同时保留必要的原始上下文，14 次全部完成，得到 35 个 Skill，总 token 约 3455.8 万。
- **C：纯切片轨迹**。只提供切片后的局部材料，14 次中 12 次完成、2 次失败，得到 27 个 Skill，总 token 约 3938.0 万，部分用量记录不完整。

模型逐组阅读后的评价显示，A 组整体质量最好，因为上下文最完整，最容易判断问题、处理和验证之间的关系；C 组效果最差，说明切片过度会损失因果信息；B 组提取数量最多，是质量、成本和规模化之间的折中。这里的质量判断来自模型定性评价，而不是统一的人工打分表。

### 2.4 选择 B 组作为后续素材

后续选择 B 组的 35 个 Skill，不是因为它在单项指标上绝对最好，而是因为它最适合作为真实系统的实验素材。B 组保留了较完整的上下文，又比完全使用原始轨迹更容易组织和扩展；同时保留了一些近似主题和噪声，可以检验检索系统面对相似 Skill、边界不清和误触发时的表现。

## 3. Skill 管理系统与真实 Agent 实验

### 3.1 管理系统设计与 DSH 接入

确定 B 组素材后，开始把 Skill 从静态文件整理成可维护、可检索、可反馈的知识库，并接入 DSH runtime。系统维护 35 个 Skill 的正文、描述、来源和指纹，接收 Agent 运行中的用户输入与工具结果，判断当前事件是否需要检索，并在检索到足够相关内容时向模型追加可选提示。

系统同时记录触发、相似度、命中与未命中、提示是否返回等信息，便于区分“没有触发”“触发但没有结果”和“结果没有正确返回”。设计中还保留了影子校验、签名检索和反馈统计接口，为后续比较高成本 embedding 检索与低成本签名检索做准备。

接入时保留了原有通用检索程序，没有把它改造成只能服务这 35 个 Skill 的专用脚本。这样既能验证管理系统，也保留了原检索程序在其他数据和任务上的独立价值。

### 3.2 三组可行性实验

为了观察管理系统能否进入真实 Agent 工作过程，搭建了三组可复现实验环境，并分别运行 managed 和 baseline：

- **Job Board**：前端 TypeScript 类型检查与修复；
- **Epilog tests**：C++ 原子表测试的编译和测试宏问题；
- **Epilog solver**：解析器输入问题和动态断言生命周期问题。

三组任务最终都完成。managed 运行过程中能够接收实时 trace、触发检索并向模型返回 Skill hint；baseline 也能独立完成任务，因此本轮结果适合表述为“管理系统已经具备真实运行可行性”，还不能表述为“已经稳定提升任务成功率”。

从成本观察，managed 的输入上下文通常更高，但三组实验的模型运行结果均可完成。Epilog solver 的 managed 工具耗时受到人工等待回复影响，不能直接视为正常工具效率。三组实验的主要价值是验证同一套管理机制可以跨前端和 C++ 项目工作，而不是进行严格的统计显著性比较。

### 3.3 Agent 反馈与当前问题

三轮会话结束后，Agent 对 Skill 内容和机制的评价比较一致：Skill 质量高，机制设计有用，推荐内容能够帮助理解当前问题。

但当前系统的命中率仍然偏低，未命中概率大于命中概率；即使提示是纯文本、不阻塞任务，频繁出现的无效提示仍会消耗模型注意力。因此目前的主要瓶颈不是 Skill 内容，而是“什么时候触发”和“没有可靠结果时是否保持安静”。

## 4. 本周结论与产出

### 4.1 主要结论

本周形成了从 30 条原始轨迹到动态管理系统的一条完整验证链：

```
30 个真实轨迹
→ 动态切片得到 97 个切片
→ 8 个细领域及结果分析
→ 行为模式聚类探索
→ A/B/C Skill 提取对比
→ 选择 B 组 35 个 Skill
→ 部署管理系统并接入 DSH
→ 在三个 fixture 上进行可行性实验
```

主要结论是：

1. 领域聚类能有效组织材料，但聚类本身不能保证得到可复用 Skill；行为模式聚类暂时没有证明能提升提取质量。
2. 完整上下文最有利于高质量 Skill 提取，纯切片容易损失因果信息；B 组更适合作为后续系统实验素材。
3. 管理系统已经能够接入真实 Agent 并完成运行闭环，但当前收益受检索触发精度限制，下一步应优先降低无效打断，而不是继续增加 Skill 数量。

### 4.2 本周产出

- 30 个真实 Agent 轨迹及处理结果；
- 97 个动态切片及来源回溯信息；
- 8 个细领域、成功/失败分类和行为模式分析产物；
- A/B/C 三组 Skill 提取结果及成本记录；
- B-selected 35 个 Skill、出处索引和描述信息；
- Skill 管理系统及 DSH 接入代码；
- Job Board、Epilog tests、Epilog solver 三组 managed/baseline fixture；
- 管理系统运行日志、成本效果记录和 Agent 定性反馈。

## 5. 下周计划

下周将围绕错误类经验进行一次从数据到运行时的整体优化。错误类轨迹通常包含明确的错误信号、排查过程和验证结果，复用价值比一般操作轨迹更高，因此下一阶段不再只关注“提取出多少 Skill”，而是关注哪些错误经验值得进入知识库、如何被准确检索，以及推荐后是否真的减少重复排查。

### 5.1 扩大并优化错误类数据集

- 在现有 30 条轨迹的基础上，继续扩大错误类轨迹的覆盖范围，优先补充具有明确错误码、异常类型、编译失败、测试失败和依赖冲突的案例；
- 按错误类型、项目环境和修复结果整理数据，区分可复用的错误经验与只适用于单个项目的偶然操作；
- 保留失败和未解决轨迹，避免数据集只包含成功案例，使后续 Skill 能够说明适用边界和不应采用的处理方式。

### 5.2 优化 Skill 提取候选类别

- 重新检查错误码、异常消息、调用栈、测试名称、依赖版本和配置变化等信号，确定更稳定的候选类别；
- 减少仅凭主题相似形成的候选，优先选择“问题信号明确、处理步骤完整、结果可验证”的轨迹；
- 比较不同候选类别的 Skill 提取质量，进一步明确哪些错误类型适合形成独立 Skill，哪些应合并为同一类经验。

### 5.3 优化切片轨迹的清洗策略

- 继续调整切片边界，重点保留错误出现、原因分析、修改动作和验证结果之间的连续关系；
- 清理重复上下文、无关工具输出和无法支持经验判断的噪声，同时避免清洗过程丢失关键错误信息；
- 对切片后的材料进行来源回溯，确保每条候选 Skill 都能回到原始轨迹核对。

### 5.4 细化管理与检索策略

- 调整检索触发条件和相似度门槛，减少没有可靠结果时对模型的无效打断；
- 继续完善用户输入、工具结果和错误事件的触发区分，优先让明显错误信号触发检索；
- 利用运行日志分析“未触发、触发但未命中、命中但未被采用”三类情况，分别优化触发、候选排序和提示呈现；
- 继续保留 embedding 检索与签名检索的比较接口，为后续在效果相近时切换到更低成本的策略做准备。

下一周的整体目标是：让错误类 Skill 从“有价值的知识材料”逐步变成“能够在正确时机被准确推荐的运行时经验”，同时控制检索成本和对模型注意力的干扰。
