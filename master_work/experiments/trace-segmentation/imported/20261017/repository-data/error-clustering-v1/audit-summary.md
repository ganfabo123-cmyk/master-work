# 两个独立 GPT-5.6 Luna 的错误组审查记录

## 最终范围

用户要求分别派一个 GPT-5.6 Luna 审查原始轨迹组、另一个审查切片组。审查中用户取消标准消息模板策略，两个代理均被中断并收到更新范围。

最终每侧只包括 native-code 14 组、exception-type 28 组，共 42 组。message-template 不计入最终统计。之前形成的初稿仅作为审计过程保留，不代表当前结论。

| 输入 | 原生码完成 | 异常类型完成 | 最终组 ID 与输入一致 | 成员 ID 与输入一致 |
|---|---:|---:|---|---|
| 原始 30 个 Session | 14/14 | 28/28 | 是 | 是 |
| 97 个切片 | 14/14 | 28/28 | 是 | 是 |

## 文件

- 原始侧：`audit-sessions-luna/audit.json`、`report.md`、`prompt.md`。
- 切片侧：`audit-slices-luna/audit.json`、`report.md`、`prompt.md`。
- 父代理结构核验：`audit-validation.json`。
- 每侧保留 `preliminary-audit.json`、`preliminary-report.md`，其中包含已经取消或被纠正的初稿判断，不能用其统计替代最终报告。

## 评审过程与可靠性

两个初稿都曾把一般修改或成功关键词当成具体错误的修复证据。父代理检查发现：DLL 错误被配到无关的指针修改、Read 返回的源码/docstring 被当作验证、链接错误被配到栈溢出处理、删除失败探针后的构建成功被当作原问题修复。这些实例已反馈给代理并要求更正。

最终报告将错误归组与经验证据分开，但两个代理对经验证据仍有明显分歧。例如，原始侧没有认可 LNK1105 的可用链，而切片侧从同一原始 Session 引用了文件占用解释和后续构建输出。完整 Session 包含对应切片的证据，因此不能单凭这种评审差异得出“切片更好”或“原始更差”。

**最终 JSON 中的 usable/candidate/unsupported 是各代理的审查意见，不是父代理已经验证的 Skill 质量标签。暂不把它们计算为真实 Skill 提取率或损失率，也不据此排名原始与切片。**

## 可支持的观察

- 原生码可以集中明确的同码失败，但包装退出状态可能重复表示底层链接器错误。
- 异常类型会把不同原因混在一起；TypeError、RemoteException 等需要进一步查看消息及上下文。
- CodeGenError、LexError 等可能只是模块或类型声明，说明当前错误识别仍有误报。
- 一个错误组可以有有价值的子集合，也可以只有错误报告而没有完整处理证据；归组成立不等于已经生成可用 Skill。

## 核验范围

父代理检查最终两份 JSON 都恰好包含各自 42 个输入组 ID，无重复无遗漏；每组声明的成员 ID 与输入一致；原始侧 222 条、切片侧 334 条来源引用对应的文件存在。

这些是结构与可回溯性核验，不等于确认每条诊断、动作与验证之间存在正确的因果关联。本轮未修改错误识别算法或原始实验产物，没有执行原始轨迹中的命令。
