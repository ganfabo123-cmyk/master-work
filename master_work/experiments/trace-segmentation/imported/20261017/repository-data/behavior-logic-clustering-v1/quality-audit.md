# 行为目标与执行逻辑聚类质量审计

## 运行规模

- 输入切片：97 条；
- 领域成员记录：314 条（细领域允许重叠）；
- 目标簇：100 个；
- 执行逻辑簇：26 个；
- cannot-link 边：57 条；
- 目标视图覆盖：287/314（91.4%）；
- 逻辑视图覆盖：310/314（98.7%）。

## D007 C++/Parser/Lexer 示例

D007 包含 27 条领域成员记录。当前结果为 9 个目标簇、4 个逻辑簇和 3 条 cannot-link 边。目标视图把 Yggdrasil/JSX 转译阶段、C API/文档、测试与调试等相近目标放在一起；逻辑视图主要分出：

- 以 Read/Edit/Write 为主的连续修改流程；
- Create/Remove/Write 的初始化和文件生成流程；
- Read/List/Test/Compile/Run 的测试验证流程；
- Thinking/浏览器工具/Git 操作组成的外部检查流程。

这说明两套表示已经产生不同的聚类结构：目标聚类更多受用户输入和任务对象影响，逻辑聚类更多受操作序列影响。

## 当前质量判断

这版已经达到“按目标”和“按执行逻辑”分开聚类的可行性目标，可以作为下一步行为模式和 Skill 抽取的输入。它还不是最终的行为语义分类器：

1. 目标簇仍偏碎，很多簇只有 2 条轨迹；这是因为同一领域内的用户目标差异很大；
2. D007 的原领域成员本身与其他领域重叠，因此会出现 Android/Web 轨迹。这个现象来自领域层成员重叠，已保留在结果中；
3. 逻辑簇可以识别工具流程，但同样的 Read/Edit/Test 模式可能服务于不同目标；
4. cannot-link 边是保守产物，兼容组只表示“没有已知冲突”，不能当作同类证明；
5. 结果没有使用成功/失败标签，后续可以把本目录的 cluster ID 与 `cluster-outcome-classification-v1` 连接起来，比较同一目标或逻辑下的成功与失败路径。

因此，当前算法已经完成行为聚类的结构分离，但下一步应优先检查目标簇是否过碎、领域成员是否需要在行为实验前去重，以及逻辑簇是否需要把工具名进一步抽象为操作类型。
