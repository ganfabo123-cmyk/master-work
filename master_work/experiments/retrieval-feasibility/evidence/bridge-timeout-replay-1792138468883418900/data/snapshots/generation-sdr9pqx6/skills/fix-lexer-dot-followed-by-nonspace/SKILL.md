# Fix parse errors when a clause-final '.' is glued to the next token

## Goal
Resolve "expected '.', got operator '.'" parse failures in concatenated Prolog-style test input by fixing the input strings so each clause-final period is followed by whitespace, without changing lexer behaviour.

## Scope
### In scope
- Parse failures on input assembled by C/C++ adjacent string literals where a clause ends with `."` and the next literal starts with a non-space character (e.g. `"...carol)."` immediately followed by `"gp(X,Y) :- ..."`), which this lexer tokenizes as an operator rather than a terminator.
- Diagnosing with temporary error-printing in the loader, locating every affected concatenation (grep for literals ending in `."`), adding the missing space, then removing the diagnostics.

### Out of scope
- Changing the lexer's rule for `.` (the observed behaviour is treated as intended; only test input is fixed).
- Genuinely malformed Prolog input.
- The separate `assert`-via-query limitation seen in the same suite, whose root cause the trace only inferred and never verified.

## Inputs
- **Parser error message** — type: tool result text. Source: a temporarily instrumented loader printing the parse result and `error_msg`. Required: yes. Constraint: must read `expected '.', got operator '.'` (or equivalent) and identify the failing clause index. Default: 无.
- **Failing load/query strings** — type: C/C++ string literals in the test file. Source: the test harness that lexes the source. Required: yes. Constraint: source built by adjacent literal concatenation. Default: 无.
- **Lexer's period-handling rule** — type: code behaviour. Source: diagnosed in the session as: `.` is a terminator only at end of input or before whitespace; otherwise it lexes as an operator. Required: yes (understanding). Constraint: the exact source of the lexer was not read in this segment; the rule is the session's diagnosis consistent with the observed error. Default: 无.
- **Grep over the test file** — type: search over literals ending in `."`. Source: tool call. Required: yes (to find every occurrence). Constraint: pattern must catch concatenated literals at line ends. Default: pattern of the form `\.\" *$`.

## Outputs
### Artifacts
- Test source literals repaired by adding a space before the closing quote of every literal that ends a clause (trajectory: three concatenations in `tests/test_solver.cpp` plus one single-string case).
- Temporary diagnostic `fprintf` calls added during diagnosis and removed again before the final run.

### Success criteria
- The loader no longer reports `expected '.', got operator '.'`; the previously failing queries execute (trajectory: `PASS  two-body rule resolves via conjunction`) and the whole suite passes (`22/22 tests passed`).
- No diagnostic prints remain in the committed test source.

### Failure criteria
- Any concatenation of the `."` + `"non-space` form remains (a grep over the test file still matches); or diagnostics are left in place; or the suite passes only because assertions were weakened.

## Preconditions
- The parser error names the terminator explicitly (trajectory: `expected '.', got operator '.'`) and is reproducible from a specific input string.
- The input is machine-generated by C/C++ adjacent string literal concatenation, so a period can end up adjacent to the first character of the next literal.
- The lexer's decision to treat a non-terminated `.` as an operator is accepted as intended behaviour; this skill fixes inputs, not the lexer.
- Edit access to the test/harness source strings is available, and a way to rebuild and rerun the failing suite exists.
If the same error occurs with a single-space-separated, hand-written source, stop and treat it as a genuine parse error instead.

## Procedure
### Step 1: Surface the real parse error with temporary diagnostics
- actions: Add temporary `fprintf(stderr, ...)` statements to the test loader printing the parse result code and `p.error_msg` whenever loading returns failure, and print the count of successfully loaded clauses.
- inputs: test harness `load()` function.
- outputs: an error line identifying both the message and how many clauses loaded before the failure (trajectory: `parse error after 1 clauses: code=2 msg=line 1: expected '.', got operator '.'`).
- cautions: do not guess from the test assertion alone — the same assertion failure can have many causes (the session first suspected shared static state).
- next condition: the message names the terminator.

### Step 2: Recognise the input shape
- actions: Inspect the failing source string as it is actually assembled, remembering adjacent literals concatenate without any separator (trajectory: `"...carol)."` directly followed by `"gp(X,Y) :- ..."` yields `carol).gp`).
- inputs: test source literals.
- outputs: identification of each concatenation point where a clause-final `.` is glued to the next token.
- cautions: single-string inputs already containing spaces are fine; the bug hides in multi-line concatenated literals.
- next condition: fix the strings.

### Step 3: Add the missing space in every affected literal
- actions: Grep the test file for literals ending in `."` at line ends and edit each so the literal ends with `. "` (space before the closing quote). Include single-string cases where a clause is followed immediately by the next clause in the same literal.
- inputs: test file; grep results.
- outputs: all clause-final periods followed by whitespace in the assembled source.
- cautions: the space belongs inside the string; do not "fix" this by changing the lexer, and do not rely on fixing only the first reported occurrence.
- next condition: all matches addressed.

### Step 4: Remove diagnostics and verify
- actions: Revert the temporary `fprintf` instrumentation, rebuild, and run the full suite.
- inputs: build command; test suite.
- outputs: previously failing tests now pass.
- cautions: one test in the same file failed for an unrelated reason (asserting a query-time `assert` whose persistence the session only inferred, never verified) — do not attribute it to this fix.
- next condition: stop when the terminator errors are gone and the suite's other results are unchanged or explained.

## Decision Rules
### When the parser error is "expected '.', got operator '.'" and the input comes from adjacent string literals
Add a space before the closing quote of every literal that ends a clause, then grep for the remaining `."` line-end occurrences and fix them all in one pass.

### When the same clauses parse correctly in an isolated repro but fail inside the test file
Compare the actual assembled source strings, not the clauses: the test file's literal concatenation can glue a period to the next token while the repro has spaces. Fix the strings rather than the engine.

### When a test in the same suite asserts a behaviour the engine cannot provide (e.g. a query-time assert whose result must survive query-arena reset)
Leave that test's scope alone or adapt it to the supported path, and record that the root cause was inferred but not verified in the traced session; do not fold it into the lexer fix.

## Invariants
- Do not change the lexer's rule for `.` to accommodate the tests; the input strings are what get fixed.
- Do not fix only the first reported occurrence — locate and fix every affected concatenation in one pass.
- Remove all temporary diagnostics added during the investigation before declaring the work done.
- Do not attribute unrelated failing tests in the same suite to this fix; report them separately with their own (unverified, in the traced case) causes.
- Do not report the suite as passing unless the full rerun output shows it.

## Common Failures
### Failure: only the first concatenation was fixed
symptoms: the same parse error reappears in another test or after another clause.
causes: adjacent-literal gluing occurs at every concatenation point where the earlier literal ends with `."`.
recovery: grep the file for literals ending in `."` at line ends and fix all matches; the trace's grep surfaced several such lines at once.

### Failure: misdiagnosis as shared-state corruption
symptoms: long investigation of static fixture state when isolated and pairwise runs behave differently from the full suite.
causes: the real difference was the input string itself (glued period), not state.
recovery: add parse-error diagnostics to the loader to obtain the concrete message before theorising; the diagnostic print immediately revealed the terminator error in the trace.

### Failure: unrelated failing test blamed on the lexer fix
symptoms: a test asserting query-time `assert` persistence still fails after all strings are fixed.
causes: a separate engine limitation (assert writes into storage that is reset between queries) — inferred in the trace but never verified by reading the builtin's code.
recovery: report it separately as an unverified hypothesis; do not fold it into this skill's result.

## Verification
- Rebuild and run the affected suite; the previously failing assertions must now pass (observed: `PASS  two-body rule resolves via conjunction`, `PASS  recursive rule — ancestor`, `PASS  backtracking finds second solution after first fails`).
- Confirm the full suite summary shows all tests passing (observed: `22/22 tests passed` for the solver suite).
- Grep the test file for literals ending in `."` at line ends and require that each such literal is followed by a space in the assembled source.
- Confirm no diagnostic `fprintf` statements remain in the harness.
- Compare other suites' results before and after to ensure nothing regressed.

## Examples
### Example 1: glued period in concatenated clause strings
input: The solver suite fails four tests while isolated repros of the same clauses pass; with temporary diagnostics the loader prints `[load] parse error after 1 clauses: code=2 msg=line 1: expected '.', got operator '.'` and `[DEBUG two-body] loaded=-1 db.clause_count=1 db.pred_count=1 arena.count=6`. The failing source is built from adjacent literals `"parent(alice, bob). parent(bob, carol)."` `"gp(X,Y) :- parent(X,Z), parent(Z,Y)."` which concatenate to `carol).gp(...)`.
procedure: Step 1 add diagnostics printing the parse result and `error_msg`; Step 2 recognise the adjacent-literal gluing; Step 3 add a space before the closing quote of each clause-ending literal (`"parent(bob, carol). "`) and fix every occurrence found by grep; Step 4 remove diagnostics, rebuild, rerun.
expected result: the parse error disappears; `PASS  two-body rule resolves via conjunction` and the suite reports `22/22 tests passed`.
parameterized values: predicate names, the test file, the grep pattern for literals ending in `."`, suite name.
