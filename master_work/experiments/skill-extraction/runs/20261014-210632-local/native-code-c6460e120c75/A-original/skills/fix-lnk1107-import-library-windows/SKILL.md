# Fix MSVC LNK1107 on a DLL by Linking an Import Library

## Goal
Eliminate the Windows linker error `fatal error LNK1107: invalid or corrupt file: cannot read at <offset>` on a DLL consumed at link time by producing a valid MSVC import library (.lib), repointing the link at that .lib, and proving the fix by building the consumer and running it through its FFI calls with exit code 0.

## Scope
### In scope
- Diagnosing `LNK1107` errors whose message names a `.dll` path supplied to the linker (e.g., an Odin `foreign import` that points at the DLL).
- Creating or refreshing a `.def` module-definition export list from the project's public C FFI header.
- Generating the import library either with `llvm-dlltool -m i386:x86-64 -d <name>.def -l <name>.lib` or by rebuilding the DLL with `clang++ ... -target x86_64-pc-windows-msvc -shared -Wl,/DEF:<name>.def`.
- Repointing link-time references from `.dll` to `.lib`, keeping the DLL beside the executable for runtime loading.
- Verifying both stages: the consumer build exits 0 with no LNK1107, and the built program runs its FFI smoke test successfully.

### Out of scope
- Linux/macOS linking of `.so`/`.dylib` (the non-Windows branch of the import declaration is left untouched).
- Linker errors other than LNK1107 (undefined symbols such as LNK2019/LNK1120, ABI or calling-convention mismatches).
- Bugs in the FFI implementation after the DLL loads successfully.
- Installing missing Windows inspection tools (`dumpbin`, `objdump`) — in the observed environment they were absent and LLVM alternatives were used instead.

## Inputs
- **Failing build output** — string — produced by the consumer build command (e.g., `odin build src -out:build\dmls.exe`) — required — must contain `LNK1107` and name the `.dll` the linker tried to read — default: 无.
- **Consumer source with the import declaration** — file path (observed: `src/bridge.odin`) — required — must contain a Windows `foreign import ... "<name>.dll"` line that can be edited — default: 无.
- **DLL sources and public FFI header** — directory (observed: `engine/epilog/` with `internals/`, `parser/`, `engine/`, `include/epilog_ffi.h`) — required — needed to rebuild the DLL and to derive the export list — default: 无.
- **Export list `.def` file** — file path (observed: `engine/epilog/epilog.def`) — required, may be created by this procedure — must contain `LIBRARY <name>` plus an `EXPORTS` block matching the FFI header — default: 无.
- **Toolchain** — environment — required — `clang++` accepting `-target x86_64-pc-windows-msvc`, plus either `llvm-dlltool` or linker support for `-Wl,/DEF:`, plus `odin` (or the equivalent consumer build tool) on PATH — default: 无.
- **Output directory for the executable** — path (observed: `build/`) — optional — the DLL must be copied next to the executable for runtime loading — default: `build/`.

## Outputs
### Artifacts
- **`<name>.dll`** — rebuilt MSVC-target shared library — location: DLL source directory (observed: `engine/epilog/epilog.dll`) — format: PE32+ DLL, x86-64.
- **`<name>.lib`** — import library consumed by the linker — location: same directory as the DLL — format: MSVC import library (observed size 4458 bytes when generated by `llvm-dlltool`).
- **`<name>.def`** — export list — location: same directory — format: module-definition file (`LIBRARY` + `EXPORTS`).
- **Updated consumer declaration** — location: consumer source (observed: `foreign import epilog_lib "../engine/epilog/epilog.lib"` in `src/bridge.odin`) — format: Odin source.
- **Updated build script** — location: Windows build script (observed: `build.bat` passing `-Wl,/DEF:<path>.def`) — format: batch file.

### Success criteria
- The consumer build finishes with exit code 0 and its output contains no `LNK1107`.
- The `<name>.lib` file exists and is non-empty next to the DLL.
- Running the built executable performs its FFI calls correctly and exits 0.

### Failure criteria
- `LNK1107` still appears, or the build exits non-zero.
- The link succeeds but the executable fails at startup (observed: exit code 123) even though the DLL sits in the output directory.

## Preconditions
- The consumer links with an MSVC-compatible linker on Windows and the produced binary can be executed on this host; otherwise stop and report the environment mismatch.
- `clang++` accepts `-target x86_64-pc-windows-msvc`, and at least one import-library route is available: `llvm-dlltool` OR linker support for `-Wl,/DEF:`; if neither exists, stop and report.
- The complete set of exported C symbols is known from the public FFI header or an existing `.def` file; without it the import library cannot be generated correctly.
- Permission to edit (a) the consumer's Windows `foreign import` declaration, (b) the `.def` file, and (c) the Windows build script; if edits are not permitted, stop and report what must change.
- Diagnostic expectations for this environment: `dumpbin`, `objdump`, `strings`, and `hexdump` may be unavailable — `file`, `llvm-nm`, and `xxd` were present in the observed session.
- No assumption that a `file` verdict of "PE32+ ... DLL" proves linkability; precondition is to check exports with `llvm-nm` before deciding.

## Procedure
### Step 1: Capture the LNK1107 error and find the link-time DLL reference
- actions: Run the failing consumer build and keep the full error text. Grep the consumer sources for the `.dll` path named in the error (e.g., a `foreign import` line).
- inputs: failing build output; consumer source tree.
- outputs: the verbatim error line (`<path>\<name>.dll : fatal error LNK1107: invalid or corrupt file: cannot read at <offset>`) and the offending declaration that feeds the DLL to the linker.
- cautions: Copying the DLL into the output directory or rebuilding the DLL without changing the link input does not clear this error — two rebuild-and-copy cycles still failed in the observed session.
- preserve: make no code changes in this step other than reading files.
- next: Proceed to Step 2 only when the DLL path in the error matches a link-time reference in the consumer (otherwise this skill does not apply).

### Step 2: Inspect the DLL's diagnostics
- actions: Run `file <name>.dll`, `llvm-nm <name>.dll`, and (if needed) `head -c 4 <name>.dll | xxd` for the `MZ` magic. Skip `dumpbin`/`objdump` if they are not installed.
- inputs: the DLL at the path named by the linker.
- outputs: the observed failing signature: `file` reports `PE32+ executable ... (DLL), x86-64`, while `llvm-nm` reports `<name>.dll: no symbols`.
- cautions: A valid PE/MZ header does NOT mean the MSVC linker can consume the DLL as a link input; missing symbols from `llvm-nm` are the actionable signal. Do not retry unavailable tools repeatedly — switch to the LLVM alternatives after the first "command not found".
- preserve: do not delete or overwrite the existing DLL yet.
- next: Always continue to Step 3; the diagnostics only inform which generation route to prefer.

### Step 3: Ensure a `.def` export list exists
- actions: Create or refresh `<name>.def` with `LIBRARY <name>` and an `EXPORTS` block listing every C function declared in the public FFI header (15 symbols were listed in the observed session, from `epilog_create` through `epilog_version_string`).
- inputs: public FFI header (observed: `include/epilog_ffi.h`).
- outputs: `<name>.def` next to the DLL sources.
- cautions: A `.def` missing an export causes an unresolved-symbol error, not LNK1107 — keep the list in sync with the header.
- preserve: an existing correct `.def` unchanged.
- next: Proceed to Step 4.

### Step 4: Produce the import library (two verified routes)
- actions — Route A (no DLL rebuild): run `llvm-dlltool -m i386:x86-64 -d <name>.def -l <name>.lib`.
- actions — Route B (rebuild DLL and import lib together): run `clang++ <flags> -I<include> -target x86_64-pc-windows-msvc -shared -Wl,/DEF:<name>.def <sources> -o <name>.dll` — the linker then prints `Creating library <name>.lib and object <name>.exp`.
- inputs: `<name>.def`, DLL sources, include directory.
- outputs: `<name>.lib` beside the DLL, non-zero size (4458 bytes observed for Route A).
- cautions: Building the DLL without `-target x86_64-pc-windows-msvc` and without `-Wl,/DEF` (e.g., from a POSIX Bash environment) produced a DLL that neither `llvm-nm` nor the MSVC linker could use — avoid that configuration.
- preserve: existing DLL build flags (optimization, include paths) other than the target and `/DEF` additions.
- next: Proceed to Step 5 once `<name>.lib` exists with non-zero size.

### Step 5: Repoint the consumer's link input from `.dll` to `.lib`
- actions: Edit the Windows branch of the import declaration so it references the import library, e.g. `when ODIN_OS == .Windows { foreign import <lib> "../engine/epilog/<name>.lib" }`, leaving the non-Windows branch untouched.
- inputs: consumer source; path to `<name>.lib`.
- outputs: updated consumer source whose link-time input is the `.lib`.
- cautions: Only the link-time reference changes; the DLL is still required at runtime and must sit next to the executable.
- preserve: all other `foreign` procedure declarations and the `.so`/`.dylib` branch.
- next: Proceed to Step 6.

### Step 6: Rebuild everything and stage the DLL beside the executable
- actions: Rebuild the DLL if Step 4 used Route A or the DLL predates the MSVC-target fix (Route B command); copy `<name>.dll` into the output directory; run the consumer build (observed: `odin build src -out:build\dmls.exe`).
- inputs: rebuilt DLL, import library, consumer sources.
- outputs: consumer build exit code 0 with no `LNK1107` in its output.
- cautions: The DLL's mere presence in the output directory is not sufficient — a session listing showed both `dmls.exe` and `epilog.dll` present while the program still exited 123.
- preserve: the staged DLL in the output directory; do not clean it away between link and run.
- next: Proceed to Step 7 only when the build exits 0.

### Step 7: Verify at runtime, not just at link time
- actions: Run the executable from the output directory and observe its FFI smoke test output and exit code; optionally run the full build script end-to-end (observed: `build.bat run`) to confirm the import library is regenerated on every build.
- inputs: built executable plus staged DLL.
- outputs: FFI query results, a PASS line, and exit code 0.
- cautions: A passing link alone does not prove the DLL loads or that FFI calls work — do not report success before this step.
- preserve: the generated `.def`/`.lib`/`.dll` and the build-script flags that regenerate them.
- next: Stop on success; on failure consult Decision Rules and Common Failures.

## Decision Rules
### When the LNK1107 message names a `.dll` and the consumer feeds that DLL to the linker
Repoint the link-time reference at a generated `.lib`. Rebuilding or re-copying the DLL alone does not clear LNK1107 — the same error persisted across two rebuild-and-copy cycles in the observed session.

### When `file` reports a valid PE32+ DLL but `llvm-nm` reports "no symbols"
Treat the DLL as unusable as a link input: generate the import library from a `.def` (Route A) and/or rebuild with `-target x86_64-pc-windows-msvc -shared -Wl,/DEF:<name>.def` (Route B). A "PE32+ ... DLL" verdict alone never clears the error.

### When `llvm-dlltool` is available and the DLL itself need not be rebuilt
Use `llvm-dlltool -m i386:x86-64 -d <name>.def -l <name>.lib`; this produced a working 4458-byte import library in the observed session, after which the consumer build succeeded.

### When a `-Wl,/DEF:` rebuild route is preferred (build-script integration)
Rebuild the DLL with `-target x86_64-pc-windows-msvc -shared -Wl,/DEF:<name>.def` so the linker emits `<name>.lib` alongside the DLL, and bake the same flags into the Windows build script so the import library regenerates whenever exports change.

### When the link succeeds but the executable exits 123 while the DLL is present in the output directory
The DLL itself is unloadable at runtime. Rebuild it with the MSVC target and `.def`, copy the fresh DLL next to the executable, and rerun; this sequence restored a passing run in the observed session.

### When `dumpbin`/`objdump`/`strings`/`hexdump` are unavailable
Do not retry them — use `file`, `llvm-nm`, and `xxd` for diagnostics instead (the observed environment had no `dumpbin`, no `objdump`, and no `--exports` support in `llvm-objdump`).

## Invariants
- Never pass a `.dll` as a link-time input on the MSVC path; only the generated `.lib` may appear in the Windows `foreign import` (or equivalent linker input).
- Keep the `.def` `EXPORTS` list synchronized with the public C FFI header.
- Always stage the DLL next to the built executable; linking against `.lib` never removes the runtime DLL requirement.
- Do not report success from a passing link alone — run the program through its FFI calls and observe exit code 0.
- Do not modify unrelated source files, the non-Windows import branch, or unauthorized build configuration while making the fix.
- Do not claim results of diagnostic commands that were not actually run (e.g., `dumpbin` in an environment where it is not installed).
- Preserve the build-script step that regenerates the import library (via `-Wl,/DEF:`) so future export changes cannot silently reintroduce a stale `.lib`.

## Common Failures
### Failure: LNK1107 persists after rebuilding (and re-copying) the DLL
- symptoms: repeated `fatal error LNK1107: invalid or corrupt file: cannot read at <offset>` naming the same `.dll` on every build, even after `file` confirms a PE32+ DLL and the DLL was copied into the output directory (observed across two rebuild-and-copy cycles).
- causes: the consumer still hands the `.dll` itself to the MSVC-compatible linker at link time; additionally `llvm-nm` reported `no symbols` for the Bash-built DLL, so it carried no usable import information. The trajectory shows the error cleared only after the link input became the `.lib`.
- recovery: generate `<name>.lib` from a `.def` (Step 4), change the Windows `foreign import` to the `.lib` (Step 5), rebuild (Step 6).

### Failure: Link succeeds but the executable exits 123 at startup
- symptoms: consumer build exits 0, yet running the binary prints only `Exit code 123` even though a directory listing shows both `<exe>` and `<name>.dll` in the output folder.
- causes: per the trajectory, the DLL had been built in a POSIX Bash environment and was unloadable at runtime despite a valid PE header (it also showed `no symbols` under `llvm-nm`); the exact loader-level reason was not inspected further.
- recovery: rebuild the DLL with `-target x86_64-pc-windows-msvc -shared -Wl,/DEF:<name>.def`, copy the fresh DLL next to the executable, rerun — the subsequent run printed the smoke-test PASS line and exit 0.

### Failure: Export-inspection tools unavailable
- symptoms: `dumpbin: command not found`, `objdump: command not found`, `strings: command not found`, `hexdump: command not found`, or `llvm-objdump: error: unknown argument '--exports'`.
- causes: those tools are not installed in this environment, and the LLVM variant uses different flags; root cause of the absences themselves was not investigated.
- recovery: switch immediately to `file <dll>`, `llvm-nm <dll>`, and `head -c 4 <dll> | xxd`; do not keep retrying the missing tools.

## Verification
- The consumer build command completes with exit code 0 and its output contains no `LNK1107` (observed marker: `Build exit: 0`).
- `<name>.lib` exists next to the DLL with non-zero size (observed: `-rw-r--r-- ... 4458 ... epilog.lib` after `llvm-dlltool`).
- When rebuilding with `-Wl,/DEF:`, the compiler/linker prints `Creating library <name>.lib and object <name>.exp` and exits 0.
- The consumer's Windows branch reads `foreign import ... "<name>.lib"` (no `.dll` in any link-time position).
- Running the executable from the output directory exercises the FFI and prints, in order: `parent(alice, bob): 1 solution(s)`, `grandparent(alice, X): 1 solution(s)`, `parent(carol, _): 0 solution(s) [expect 0]`, `parent(X, Y): 2 solution(s) [expect 2]`, `=== Bridge smoke test: PASS ===`, then `Exit: 0` (counts are the observed project's smoke test; substitute the target project's own FFI assertions).
- End-to-end script run (observed: `build.bat run`) prints `[engine] Built ...\<name>.dll + <name>.lib`, then `[odin] Built ...\<exe>`, then the same runtime PASS output — confirming the import library is regenerated on every build rather than being a stale one-off artifact.

## Examples
### Example 1: Odin foreign import of a C++ engine DLL fails with LNK1107
- input: build output containing `d:\...\epilog.dll : fatal error LNK1107: invalid or corrupt file: cannot read at 0x2F8`; consumer file `src/bridge.odin` containing `foreign import epilog_lib "../engine/epilog/epilog.dll"`; DLL sources under `engine/epilog/{internals,parser,engine}` with FFI header `include/epilog_ffi.h`.
- procedure: Step 1 confirms the error names the DLL referenced by `foreign import`; Step 2 shows `file` → `PE32+ ... (DLL)` but `llvm-nm` → `no symbols`; Step 3 writes `epilog.def` listing the 15 exported `epilog_*` functions; Step 4 Route A runs `llvm-dlltool -m i386:x86-64 -d epilog.def -l epilog.lib`; Step 5 edits the Windows branch to `foreign import epilog_lib "../engine/epilog/epilog.lib"`; Step 6 rebuilds the DLL (Step 4 Route B: `clang++ ... -target x86_64-pc-windows-msvc -shared -Wl,/DEF:epilog.def ... -o epilog.dll`), copies it to `build/`, and runs `odin build src -out:build\dmls.exe`; Step 7 runs `build\dmls.exe`.
- expected result: the build prints no LNK1107 and exits 0; the program prints `=== Bridge smoke test: PASS ===` and `Exit: 0`.
- parameterized values: engine name `epilog`; export list from `include/epilog_ffi.h` (15 symbols observed); source globs `internals/*.cpp parser/*.cpp engine/*.cpp`; DLL output dir `engine/epilog/`; exe output dir `build/`; consumer `src/bridge.odin`.

### Example 2: Making the import library reproducible in the build script
- input: the working manual DLL build flags `-target x86_64-pc-windows-msvc -shared -Wl,/DEF:epilog.def` plus the existing Windows build script.
- procedure: bake `!CXX! !CXXFLAGS! -shared -Wl,/DEF:!EPILOG_DIR!\epilog.def !EPILOG_SRCS! -o "!EPILOG_DLL!"` into the engine-build section of the script, then run `build.bat run`.
- expected result: the script prints `[engine] Built engine\epilog\epilog.dll + epilog.lib`, then `[odin] Built build\dmls.exe`, then the runtime smoke-test PASS output — i.e., every clean build regenerates both the DLL and its import library.
- parameterized values: script name `build.bat`; variables `EPILOG_DIR`, `EPILOG_DLL`, `EPILOG_SRCS`; mode flags (`engine`, `run`, `clean`) as supported by the project's script.
