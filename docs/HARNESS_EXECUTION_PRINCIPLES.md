# CodeHarness 执行与需求理解原则

## 目标

CodeHarness 不只要能调用模型、工具和 Trace，还应当是一个可控、可审计、不会擅自扩大任务的开发 Harness。它应帮助使用者明确知道：系统理解了什么、准备做什么、实际改了什么，以及哪些能力尚未启用。

## 应具备的优势：变更可审计

每次完成文件修改后，Harness 应输出简短的变更清单：

- 新增了哪些文件；
- 修改了哪些文件；
- 每个文件的目的是什么；
- 是否运行了验证，以及验证范围。

这不是冗余的工作日志，而是交付的一部分。代码变更往往跨越 Prompt、Agent、Runtime、CLI、Trace 和配置；没有文件级摘要，使用者难以快速判断改动边界，也难以发现未经授权的扩张。

### Prefer / Not Prefer

- Prefer：用“文件路径 + 一句话目的”报告实际变更。
- Prefer：区分“本次新增”“本次修改”“已存在但未改动”。
- Prefer：如实说明未运行、只做静态检查、或完成端到端验证。
- Not Prefer：只说“已完成”，让使用者自己翻 diff 才知道发生了什么。
- Not Prefer：把历史未提交改动混进本次结果，却不说明其来源。

## 需求理解的通用失败逻辑

需求理解偏差通常不是模型没有读懂句子，而是执行者把自己的默认方案置于用户当前指令之上。常见的通用错误有以下几类。

### 1. 用推测替代明确边界

执行者看到一个目标后，自动补齐“应该还需要”的实现、验证、重构或体验设计。这会把“运行”“解释”“只做 CLI”之类的窄任务，变成未经授权的完整方案。

- Prefer：把用户明确说出的对象、动作、约束和禁止项作为任务边界。
- Prefer：只有发现执行所必需的缺失信息时，才提出最小澄清。
- Not Prefer：为了“完整”“健壮”“顺手”自行增加功能、改造或测试。

## 需求复述，先对齐再执行

用户提出需求后，默认先用简短的话复述自己理解的需求，再开始实质动作。复述让用户能在代码修改前纠正对象、范围、限制条件和完成标准，从源头避免双方理解不一致造成错误实现。

复述应当简短且忠实保留用户的限定词，例如“只做”“不要改”“这轮”“先规划”。它不是重新设计需求，也不应在复述中加入执行者自己的推测。

只有用户明确要求“不用复述”“直接做”或同等含义时，才省略复述并直接执行。

### Prefer / Not Prefer

- Prefer：每次新需求先简短说出“我理解为：…”。
- Prefer：将用户指定的对象、动作、限制和不做事项逐条保留。
- Prefer：复述后立即执行已明确的最小范围，不把复述变成反复确认的阻塞。
- Not Prefer：默默按自己的技术理解开工，等产生 diff 后才暴露理解差异。
- Not Prefer：把复述写成包含未授权设计方案的长计划。

### 2. 把历史上下文覆盖当前指令

历史约束可以提供背景，但不是永久指令。用户当前一句话如果重新限定范围，应优先按当前范围解释。

- Prefer：以最新、最具体、直接作用于当前任务的指令为准。
- Prefer：明确区分“本轮限制”“长期约定”“已经结束的测试条件”。
- Not Prefer：把上一轮讨论过的参数、命令形式或实现方案自动带入当前任务。

### 3. 把自然语言对象偷换成技术实现

“一次请求”“CLI 式入口”“重跑”描述的是用户目标或交互语义，不等价于某个预设技术参数。把它们直接替换为 `max_turns=1`、内联脚本或某种固定命令，属于未验证的语义偷换。

- Prefer：先说明对业务语义的理解，再映射到技术实现。
- Prefer：当一个词同时可能表示用户输入次数、模型轮数或工具调用数时，保持它们的区分。
- Not Prefer：把最方便实现的技术解释当作唯一解释。

### 4. 用隐藏控制代替真实能力

为了让模型得到期望格式，在 Prompt 中加入额外的强制指令，可能让演示“成功”，但掩盖了真实的 Agent 能力、工具选择和输出可靠性。

- Prefer：让 Prompt、工具、输出格式和运行协议的职责公开、可追踪、可配置。
- Prefer：在 Trace 中完整暴露实际发送给模型的消息。
- Not Prefer：加入未向用户说明的提示词、反馈回路或特殊捷径来促成结果。

## 编码前的最小实现计划

任何代码修改前，Harness 应先给出可审阅的计划。计划不是大而全的架构蓝图，而是本次可执行的最小实现边界。

每个计划项应分成两部分：

| 内容 | 含义 |
| --- | --- |
| 最小实现 | 为满足当前明确需求必须做的改动；默认执行。 |
| 扩展点 | 可以自然延伸的能力、后续配置或更复杂的架构；默认不做。 |

### 计划模板

1. 最小实现：要改的文件、要新增的最少接口、可观察的完成结果。
2. 扩展点：未来可能支持什么，以及为什么本次不实现。
3. 验证范围：只做静态检查、单元测试、真实模型运行，或不验证；必须与用户授权一致。

### Prefer / Not Prefer

- Prefer：先列最小实现计划，用户确认或直接要求“做”后再编码。
- Prefer：把扩展点放在计划旁边，明确标记为“不默认执行”。
- Prefer：在用户指定扩展功能时，再将该扩展点升级为实现项。
- Not Prefer：把可能有用的扩展能力混入默认实现。
- Not Prefer：先写代码，再用事后解释替代计划确认。

## 运行与修改的默认边界

- 用户说“运行、重跑、看日志、解释、排查”时，默认执行或读取，不修改代码。
- 用户说“修改、实现、做”时，只实现当前计划中的最小实现部分。
- 用户说“先规划、列计划、讨论”时，不写代码。
- 任何需要跨出当前边界的行为，应先单独指出扩展点并等待用户指定。

## 阶段性提交，保留可恢复节点

较大改动完成，或一项明确的基础能力已经达到阶段性可用状态时，应主动建议用户提交一次代码。这样后续继续尝试新设计、修复问题或运行实验时，都有一个用户确认过的稳定恢复点。

如果环境提供 `ask user` 一类追问工具，应使用该工具询问用户是否要提交当前阶段；如果没有该工具，则在完成摘要中简短建议提交，但不得擅自执行 `git commit`。

### Prefer / Not Prefer

- Prefer：在大范围重构、关键能力打通、或用户确认阶段性结果后，建议创建一次提交。
- Prefer：说明建议提交的原因和当前提交应包含的文件范围。
- Prefer：后续试验性改动在新的工作区状态上进行，避免污染已确认的阶段成果。
- Not Prefer：持续叠加未经确认的修改，直到出现错误后只能依赖用户手动回撤。
- Not Prefer：未经用户明确授权自行提交、覆盖或回退 Git 历史。

## 典型反馈后，请求沉淀经验

收到典型成功或失败反馈后，应先询问用户是否允许总结这次经验，而不是自行把一次反馈写成永久规则。典型反馈包括：用户明确认可或否定结果、同类问题重复出现、关键运行成功或失败、以及用户指出了具体行为偏差。

用户允许后，经验必须记录实际发生时间，精确到分钟；成功或失败由用户反馈推测，并明确写出推测依据。经验不能只描述表面现象，必须分析背后的成功或失败机制，以及可迁移的改进原则。

### 经验模板

```text
在 {YYYY-MM-DD HH:mm}，我做了 {事情}。
反馈为 {成功 / 失败}（根据用户反馈 {推测依据}）。

当时我的做法是：
{具体做法}

我需要深刻思考一下这次成功/失败的背后原因：
为什么我能成功/失败，我认为原因是：
{原因分析与可迁移原则}
```

本节中的所有经验举例都必须使用上面的模板；不再使用脱离时间、做法、反馈和原因分析的零散叙述。

### 经验：通用协作平台不得承载领域工作流

在 2026-08-07 11:44，我在多 Agent 协作平台中把狼人杀的 Session、回合推进、角色、规则引擎、状态持久化和消息组装直接写进了通用 `Orchestrator`。
反馈为失败（根据用户指出项目目标是通用多 Agent 协作平台，而不是狼人杀项目，并要求所有领域私有逻辑迁出通用调度器）。

当时我的做法是：
为了快速跑通演示，把创建私聊 ROOM、角色成员、`game-engine`、游戏 phase、工具选择、游戏状态事件和恢复逻辑都放进了 `Orchestrator` 的私有方法与 `run_room_turn()` 分支中。虽然功能可运行，但通用 ROOM 调度、Trace、上下文管理与狼人杀 workflow 被耦合在同一个文件里；新增另一种协作任务将被迫修改已有游戏分支，且难以判断哪些逻辑可复用。

我需要深刻思考一下这次成功/失败的背后原因：
为什么我失败，我认为原因是：
把“当前演示要运行”误当成“基础设施应该知道该演示的业务语义”，没有先按可复用性划分边界。以后实现多 Agent 协作功能时，必须先分类：ROOM 消息领取与按 room ID 分组、`RoomTurnContext`、增量 history、Trace 追加、Agent factory/Profile 恢复、canonical 消息回放、原子持久化、公共 ROOM 可见性等属于框架层；角色、领域状态、回合或工作流推进、领域工具、领域 Prompt、私有 ROOM 成员规则、业务事件内容和终止规则属于 workflow 层。通用模块只能提供无业务名词的接口和数据结构，不能出现某个领域的条件分支、常量、类型、文件名或私有方法。每个新协作任务应仅在 workflow/任务入口组装领域策略，复用框架 API；若发现某段逻辑可被两个以上场景使用，先抽为通用接口并为其写独立回归，再接入具体 workflow。

### Prefer / Not Prefer

- Prefer：在典型反馈出现后，先询问用户“可否总结这次经验”。
- Prefer：获得允许后，按模板记录真实时间、行为、反馈推测、当时做法和深层原因。
- Prefer：从具体记录中抽取可迁移原则，但不把未经用户确认的推测伪装成事实。
- Not Prefer：收到一次评价就自动写入长期经验，或跳过用户确认。
- Not Prefer：只写“成功了”或“失败了”，却不分析导致结果的机制。

### 经验：模型输入、审计记录与运行诊断必须分层

在 2026-08-07 11:44，我在多 Agent 工作流中检查了 Trace、模型 messages 与运行卡住后的状态。
反馈为成功（根据用户明确要求将可迁移的 Trace、缓存审计和故障诊断原则直接沉淀给后续 Code 助手）。

当时我的做法是：
将 JSONL 作为可恢复的事实源，同时把 Markdown 作为可读投影；检查每回合模型实际收到的 messages，而不是仅根据日志文件大小判断缓存效率；在工作流停滞时按 Trace、持久化状态和运行日志定位问题。

我需要深刻思考一下这次成功/失败的背后原因：
为什么我能成功，我认为原因是：
可恢复性、可读性、模型上下文和运行状态是不同层次，不能由同一份“好看”的输出替代。以后必须保持原始 Trace 无损且可 replay，Markdown 等展示层只能做非破坏性解码；日志按增量线性写入不代表模型调用成本线性，缓存与 token 优化必须审计每次真实发送的 messages 是否保留稳定前缀、是否仅追加新事件；运行卡住时必须先区分模型未行动、工具不可用或被拒绝、领域状态机未推进、持久化或恢复失败，并用对应的 Trace、状态文件和日志证据定位，禁止仅凭界面现象猜测原因。

### 经验：演示场景验证平台能力，不定义平台语义

在 2026-08-07 11:55，我用狼人杀工作流验证多 Agent 协作平台的私聊、公共讨论、状态恢复和工具行动能力。
反馈为成功（根据用户要求将狼人杀明确定位为测试场景，而非框架本体，并要求该边界沉淀为长期经验）。

当时我的做法是：
将狼人杀作为端到端验收：它要求多个 Agent 协作、部分消息仅对特定参与者可见、工作流能在中断后恢复、Agent 能发起并接收受规则约束的行动。但实现时不把狼人身份、夜晚阶段、击杀规则、女巫药水或胜负判断定义为平台概念。

我需要深刻思考一下这次成功/失败的背后原因：
为什么我能成功，我认为原因是：
演示场景用于证明平台接口足够，而不是为通用模块提供业务名词。以后应把“创建协作空间、投递消息、控制可见性、恢复会话、追加上下文、记录 Trace、调度单个 Agent 回合”实现为平台能力；把角色身份、领域状态、回合流程、业务规则、领域工具、Prompt 和终止条件留在具体 workflow。若将来换成规划 Agent、审查 Agent、执行 Agent 的协作任务，应新增或替换 workflow 来组装这些平台 API，而不应修改平台层以加入新的业务分支。

### 经验：多 Agent 协作必须分离事件、投递与消费

在 2026-08-07 11:56，我实现了多个 Agent 之间的协作通信、重试和会话恢复。
反馈为成功（根据用户确认将该协作模型沉淀为不依赖具体 ROOM 实现的长期经验）。

当时我的做法是：
曾把一条协作消息同时当作业务事实、收件箱内容、前端展示内容和模型上下文，分别在多个位置保存和处理；之后将它们拆分为事件、投递和消费三个概念。

我需要深刻思考一下这次成功/失败的背后原因：
为什么我能成功，我认为原因是：
多 Agent 协作无论表现为 ROOM、队列、任务看板、共享事件流还是 Agent 间 RPC，本质都包含三层。事件是不可变协作事实，必须有稳定 `event_id`、会话 ID、发送者、内容、创建时间和可见范围，正文只保存一份；投递记录事件应交给哪些消费者，只保存 `event_id`、目标和投递状态，广播是多条投递而不是多份消息；消费记录某个 Agent 是否已读取或处理该投递，必须按 `event_id` 幂等，重试、恢复或快照滞后时不得重复产生业务副作用。模型上下文只是某个 Agent 对有权看到且尚需处理事件的增量投影，前端只是授权事件的展示投影，业务状态机只消费合法事件并产生新事件。访问控制必须在事件查询和投递边界执行，不能只靠前端隐藏。以后实现协作能力时必须先明确这三层，即使替换 ROOM、队列或其他通信实现，协作语义也应保持一致。

## 完成标准

一次 Harness 任务的完成不只是“代码能跑”。它还包括：需求边界没有被擅自扩大、Trace 能说明真实行为、变更文件可审计、以及用户能以稳定入口复现该行为。
