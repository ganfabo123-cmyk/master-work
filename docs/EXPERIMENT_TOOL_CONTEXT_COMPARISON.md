# 实验：原生工具协议与文本压缩工具上下文对比

## 实验目的

验证在工具调用链中，把原生的 `assistant tool_calls → tool result` 消息替换为文本摘要是否可行。

对比的压缩策略为：在每次工具执行后向模型传入一段文本，包含工具名、输入参数、工具结果，并追加“如果要结束任务，调用 `submit_*` 完成”的提示。

Trace 仍保留完整原生工具调用与工具结果；本实验只改变下一轮发送给模型的上下文。

## 实验设置

- 时间：2026-08-05 19:23
- 模型：`deepseek-v4-flash`
- 任务：评估发布 `rel-2026.08.05.17` 是否应立即回滚。
- 每侧次数：10 次。
- 工具调用流程：必须串行完成三轮。
  1. `get_release_snapshot`
  2. `analyze_service_signals`
  3. `evaluate_rollback_gate`
- 最终输出：观察模型是否调用 `submit_release_assessment`。

## 结果

| 策略 | 三轮工具完成 | 最终 submit | 平均输入 token | 平均输出 token | 平均总 token | 平均耗时 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 原生工具协议 | 10 / 10 | 10 / 10 | 5293.0 | 733.0 | 6026.0 | 8061.93 ms |
| 文本压缩 + submit hint | 6 / 10 | 6 / 10 | 3842.8 | 672.4 | 4515.2 | 7155.24 ms |

压缩策略约节省 25% 总 token、约降低 11% 延迟，但有 4/10 次违反了要求的串行工具协议，三轮工具完成率和最终结构化提交率均从 100% 降至 60%。

## 结论

原生工具调用协议明显更可靠。工具调用、调用 ID、参数与工具结果之间的关联，不应在当前或最近相关上下文中被替换成普通叙述文本。

文本压缩可以作为旧上下文的节流手段，但不能承担以下职责：

- 当前工具调用链的协议表达；
- 工具结果与调用的精确关联；
- 多 Agent 间的结构化数据交接；
- `submit_*` 输出可靠性的主要保障。

追加 `submit` hint 提高的是提示强度，不是输出协议的可靠性；本实验中的压缩侧同时改变了“上下文表示”和“提示内容”，因此不能将结果全部归因于压缩本身，但它足以证明该组合策略不适合作为默认执行协议。

## 对多 Agent 工作流的设计影响

多 Agent 协作不应通过压缩或转发完整聊天历史实现。应由 Orchestrator 维护独立的 `WorkflowState`，以经过 Pydantic 校验的 artifact 作为交接物。

```text
Agent 内部：原生 messages + 原生 tool_calls + tool results
    ↓
Agent 完成：OutputFormat 校验为结构化 artifact
    ↓
Orchestrator：写入 WorkflowState
    ↓
下一 Agent：读取与自身任务相关的 artifact 投影
```

`OutputFormat` 的定位应是“工作流交接产物契约”，而不是“压缩模型工具上下文的格式”。

建议的最小 artifact 元数据：

- `producer_agent`
- `schema_name`
- `validated_payload`
- `trace_session_id`
- `created_at`

为什么我能成功/失败，我认为原因是：

实验将工具链设计为必须读取上一工具返回值才能进入下一步骤，因此能直接测量上下文表示是否保留了工具协议语义。原生 API 消息保留了调用与结果的结构化关联；文本摘要虽然减少 token，却把协议退化为自然语言叙述，导致模型更容易跳步或偏离既定工具顺序。未来应将“模型执行历史”和“工作流结构化交接”分成不同层，而不是让一种压缩消息同时解决两者。
