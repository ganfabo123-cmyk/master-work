# 需求理解偏差复盘

## 结论

本次反复理解错需求，不是需求本身不清楚，而是执行时擅自补全了用户没有提出的设计、约束和后续动作。每一次多做一步，都会把原本明确的目标改成另一个目标。

## 具体偏差

### 1. 把一句话中的旧约束当成了当前约束

用户先前说过“本轮只允许发一次请求”。随后明确解释：这里的“一次请求”是指只注入一个用户问题，而不是限制模型只能进行一个 LLM turn。

错误做法是继续把它解释为 `max_turns=1`，导致工具调用后无法让模型读取工具结果并完成答复。

正确做法是区分：

- 用户输入次数：初始 `user` message 的数量；
- 模型调用轮数：Agent 与工具之间允许的 LLM 往返次数；
- 工具调用次数：单个 assistant 回复中可包含的工具调用数量。

除非用户明确限制模型轮数，否则不能把“一个用户请求”改写成“一轮模型调用”。

### 2. 把“重跑”擅自扩展为“先改代码再跑”

用户要求重跑时，目标是验证当前行为和 Trace，而不是授权重构 Agent 的输出流程。为了解决潜在的结构化输出问题而修改 `Agent.run`，属于超出授权范围的实现扩张。

正确做法是：

1. 按当前代码直接运行；
2. 如运行失败，先报告失败证据；
3. 只有用户明确说“改”或“修复”时，才提出并执行代码修改。

### 3. 把“不要作弊提示”错误扩展成一整套输出协议改造

用户指出 Trace 中不应存在未经说明的结束任务提示。这个问题的直接目标是删除或停用该额外提示，而不是自行设计新的隐藏结束机制。

正确做法是只处理被指出的行为，并先说明改动边界：删除哪段提示、是否保留工具、运行会有什么可观察结果。任何输出格式策略的重新设计，都需要用户另外授权。

### 4. 没有先逐条复述当前需求

用户此前已经明确要求：每次实质工作前，先逐条复述当前需求。实际执行时没有稳定遵守，导致“重跑”“一次请求”“CLI 式入口”等短句被按自己的默认假设解释。

正确格式应为：

> 我理解本次只要求：1. …；2. …；3. 不做 …。

复述必须保留用户定义的对象、范围和否定条件，不得把“这个请求”“这轮”“只做”换成自行推断的技术实现。

### 5. 把用户的约束替换成了自己设计的约束

用户说“只做 CLI 式入口”时，错误地重新带入了此前讨论过的“20 字以内命令”、交互式输入、客服专用命令等内容。这些都不是该次任务的要求。

正确做法是：当前一句明确限定范围时，只执行该范围；以前的讨论除非被用户重新提及，不能自动恢复为本次约束。

## 后续执行准则

1. 每次开始实质动作前，按条复述本次需求，尤其保留“只”“不要”“这轮”“当前”等限定词。
2. 用户要求运行、检查、解释或展示时，默认只读或执行，不修改代码。
3. 用户要求修改时，只修改他点名的对象；需要扩大范围时先停下说明。
4. 上一轮的限制不自动继承到下一轮；只有用户重复确认的约束才继续生效。
5. 发现歧义时，不用自行设计补丁填补；先用最小、可验证的解释或问题确认。

## 本次应承担的责任

问题在于执行者没有把用户的话当作唯一的任务边界，而是不断用自己的“可能需要”“为了保证”“顺便处理”去替换用户已给出的明确指令。之后应以用户当前句子的精确范围为准，而不是以推测出的完整方案为准。
